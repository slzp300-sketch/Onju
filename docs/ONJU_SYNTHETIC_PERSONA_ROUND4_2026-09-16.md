# 온주 4차 가상 사용자 20명 진단·작업로그

작성: 2026-09-16. 사용자 요청: “좋아 가상 사용자 20명 만들어서 한번 더 진행해보자.”

## 결론

기존과 겹치지 않는 **한국어 10명·영어 10명, 22~49세의 가상 설정**을 추가했다. 작성 여정 발언 **83개**, 별도 상태 경계 검사 **38개**, 실제 에이전트의 정보 기록 처리 경로 검사 **10개**로 총 **705개 조건**을 확인했다.

**652개 통과 / 53개 실패**가 동일 소스에서 두 번 재현됐다. 중복·후속 실패를 묶으면 **11개 보완 유형**이다. 기존 25명의 상태 조건 739개와 기존 테스트 1,015개는 그대로 통과했다.

우선 보완 대상은 **거절·조건부 발언을 확정으로 저장**, **타인·과거 정보를 본인의 최신 정보로 저장**, **날짜 원문과 정규화 값의 불일치 허용**이다. 고정 답변을 더 추가하는 문제가 아니라, 저장 후보의 대상·시점·확정 여부와 검증 범위를 일관되게 다루는 문제다.

이번에는 **진단 데이터·실행 도구·보고서만 추가**했다. 제품 수정·배포·운영 DB 변경·유료 모델 요청은 하지 않았다.

## 결과를 해석하는 기준

- 누적 가상 설정 **45명**, 실제 참여자 **0명**이다. 한국·미국의 대표 표본이나 설문 결과가 아니다.
- 직장·학업·육아·돌봄·이직·자영업에서 일어날 법한 상황을 가정했다. 실제 발생 빈도는 조사하지 않았다.
- 사람 역할의 발언, 기대 상태, 모델이 전달할 법한 구조화 후보는 모두 작성된 테스트 데이터다. **실제 온주 모델의 자연어 추출 결과가 아니다.**
- 83개 기본 여정의 상태 조건은 모두 통과했다. 실패는 확장한 의도·대상·기간·계산 경계에서 나왔다. 53개 실패가 53개의 독립 버그라는 뜻은 아니다.
- 20개 설정 중 18개에 실패 조건이 있지만, 이는 의도적으로 까다로운 경계를 고른 결과다. “사용자 90%가 실패한다”는 통계로 해석하면 안 된다.
- 만족도·재방문·실행률·지불 의향은 측정하지 않았고 결과 데이터에도 `null`로 남겼다.

## 검사 방식과 구분

1. **기본 여정:** 기간·분야·현재 수준·원하는 결과·실행 여건을 순차 또는 묶음으로 입력하고 상태를 확인했다.
2. **의도한 후보:** 유효한 자연어에서 합리적으로 추출한 후보가 저장되는지 검사했다.
3. **잘못된 후보:** 거절한 수량, 타인의 성과, 잘못 정규화한 날짜처럼 서버가 차단해야 할 후보를 의도적으로 주입했다. 모델이 실제로 그런 후보를 내는 확률을 측정한 것은 아니다.
4. **짝지은 대조군:** 같은 의도를 짧고 명확하게 표현하거나 올바른 정규화 값으로 보내 비교했다. 대조군은 모두 통과했다.
5. **에이전트 경로:** 실제 `runAgentTurn`의 라우팅·후보 필터·저장 도구 처리 결과를 확인했다. 10개 중 9개는 저장 도구의 결과가 반환된 경계에서 의도적으로 멈췄고, 1개는 인라인 모의 답변까지 반환됐다. 완전한 실행 초안 생성이나 실제 사용자와의 한 턴 전체를 평가한 것이 아니다.

에이전트 경로의 모의 요청 함수 진입은 26회, 작성된 모의 응답 반환은 17회였다. 9회는 저장 결과를 관찰하고 종료하기 위한 진입이다. **공급자 API 호출은 0회**이며 이 내부 횟수를 유료 호출 횟수로 세지 않는다.

검사 준비 단계에서 모의 최종 답변의 초안 규약 불일치, 잘못된 대화 상태 enum, 라우팅의 필수 `reason` 누락을 확인했다. 제품을 바꾸거나 기대값을 낮추지 않고 **실행 도구만 수정**했다. 현재는 실제 요청 스키마로 모의 응답을 검증하고, 초안을 가짜로 만들지 않고 저장 처리 경계에서 검사한다. 최종 두 실행의 준비 오류는 0개다. 초기 결과 폴더는 보존하지만 최종 결함 수에는 사용하지 않는다.

근거 누락 차단을 검사하는 KR-23의 한 후보만 의도적으로 원문에 없는 근거를 포함한다. `allowUngroundedEvidence: true`로 표시하여 테스트 데이터 사전 검사를 건너뛰되, **제품의 근거 검증은 그대로 실행**했다. 이 후보는 정상 차단됐다.

## 발견한 11개 보완 유형

### 1. 거절·조건부 표현의 값을 확정 저장 — P1, 14개 실패 조건

사례: KR-16, US-11, US-15, US-17. 저장 함수뿐 아니라 실제 에이전트의 기록 처리 경계에서도 재현됐다.

- `책 6권 완독은 안 할래. 원래 목표를 유지해줘.` → 기존 3권이 거절한 6권으로 바뀜.
- `If the client delays the launch, change the period to 12 weeks. No change for now.` → 조건이 성립했다는 확인 없이 8주가 12주로 바뀜.
- `Don’t move the deadline to November 30, 2026.` → 곡선 `’`를 쓰면 금지한 날짜로 바뀜. 직선 `'`를 쓴 대조군은 차단됨.
- `I can't spend 3 hours per week. Keep the old time budget.` → 불가능하다고 말한 3시간을 가용 시간으로 저장.

원인: `goalEvidenceScope.ts`와 `goalIntakeEvidence.ts`의 일부 부정 표현·동사 목록 검사, 가용 시간의 단어 존재 검사가 **확정 여부를 필드마다 다르게 처리**한다. 현재 발언에 숫자가 있다는 조건만으로는 변경 권한을 증명하지 못한다.

개선 기준: 같은 정규화 및 확정/거절/조건부 판정을 모든 변경 필드에 적용하고, 범위에 해당하는 부정·조건을 근거에서 잘라 내지 않게 검증한다. 사용자에게 다시 긴 입력 양식을 요구하지 않는다.

### 2. 타인의 성과·목표를 사용자 것으로 저장 — P1, 5개 실패 조건

- KR-21: `동료는 프로젝트 5개를 완성했대. 나는 아직 프로젝트 1개야.`에서 동료의 문장을 근거로 본인 현재 수준을 5개로 바꿀 수 있음. 에이전트 기록 경계도 동일.
- US-13: `My colleague's goal is 8 articles. Keep my original goal.`에서 동료의 8편을 본인의 기존 3편 목표 대신 저장할 수 있음.

원인: 정확한 원문 포함 여부와 분야·수치 형식은 확인하지만 **그 사실의 주체가 사용자 자신인지** 확인하는 공통 경계가 없다.

개선 기준: 본인·타인·인용·예시를 구분한 사실 후보를 만들고, 사용자에게 속하는 사실만 개인 계획에 반영한다. 추출 필터와 최종 저장 함수가 같은 기준을 써야 한다.

### 3. 현재를 다시 말하지 않고 과거만 회고하면 최신 값을 덮어씀 — P1, 3개 실패 조건

KR-20: 현재 책 1권을 완료한 상태에서 `작년에는 책 0권을 읽었어. 그때는 육아 때문에 어려웠지.`를 회고했는데 0권으로 교체 가능했다. 에이전트 기록 경계도 동일했다.

직전 보완은 같은 발언에 과거와 현재가 함께 있을 때 과거 절을 차단했다. 이번에는 과거만 회고하고 현재 정보는 저장 상태에만 있는 경우다. `goalFactCanReplace`가 발언 전체의 ‘지금/현재’ 신호에 의존해 이 경우를 통과시킨다.

개선 기준: **현재를 반복해서 말하지 않아도 저장된 최신 사실을 보호**한다. 과거 회고는 별도 맥락으로 보존하고, 현재 값 정정이라는 근거가 있을 때만 교체한다.

### 4. 정보와 별도 질문이 함께 있으면 일부 필드에서 저장 거절 — P2, 9개 실패 조건

- KR-17: `최근 완성한 영상은 2편이야. 다음에는 뭘 할까?` 전체를 근거로 보내면 현재 수준 갱신을 거절한다. 실제 에이전트 필터에서도 1편이 유지됨.
- KR-18: `주당 2시간 가능해. 어떤 요일로 나누면 좋을까?` 전체 근거는 시간 갱신을 거절한다.
- KR-19: `일본어는 제외해줘. 독서는 어떤 책이 좋을까?`는 다른 목표의 질문 때문에 일본어 제외도 막힌다.

앞선 보완에서 목표 결과는 근거 절 단위로 처리했지만, 현재 수준·시간·목표 제외는 여전히 근거 전체 또는 사용자 발언 전체의 물음표를 검사하는 경로가 남았다. 근거를 좁히거나 별도 질문을 빼면 대조군은 통과했다.

개선 기준: 모든 저장 필드와 행동에 같은 절 범위 검증을 적용한다. “확정 정보 기록 + 별도 질문에 답하기”를 공통 동작으로 다룬다.

### 5. 정중한 의사 표현을 미확정으로 오해 — P2, 2개 실패 조건

US-12: `I would like to finish 4 books.`는 질문이 아닌 목표 변경 의사지만 `result_not_decided`로 거절됐다. `I want to finish 4 books.`는 통과했다.

원인: `goalResultIsDecided`가 `would`를 일괄적으로 미확정 표현으로 본다. 개선 기준은 질문·조건부와 정중한 확정 의사를 구분하는 것이다.

### 6. 대조 접속사로 연결한 유지·제외 대상 구분 실패 — P2, 4개 실패 조건

US-14: `Remove drawing, but keep writing.`에서 그림 제외가 거절된다. 실제 에이전트 기록 경계도 같다. 세미콜론으로 나눈 대조군은 통과했다.

원인: `explicitAreaChange`가 일부 `and` 및 문장부호는 분리하지만 `but` 절을 분리하지 않아, 다른 대상의 `keep`가 제외까지 차단한다. 개선 기준은 행동별 대상 범위를 접속 표현과 무관하게 유지하는 것이다.

### 7. 빈도 표현 지원 공백과 누적량 오해 — P2, 5개 실패 조건

- KR-22: `주 2회`는 주간 속도 2회로 비교하지 못해 `needs_rate`. `주당 2회`는 `ready`이고 주간 속도도 맞음.
- US-16: `2 articles every fortnight`는 주 1편인데 주기 없는 누적 2편처럼 해석한다. 4주에 12편 목표에서 필요한 주간량을 3편 대신 2.5편으로 계산한다. `every 2 weeks` 대조군은 현재 주 1편·필요 주 3편·`strained`로 맞게 계산한다.

원인: `goalQuantity.ts`가 지원하지 않는 주기 표현을 발견했을 때 주기 없는 누적량과 구분하지 못한다. **`ready`로 잘못 통과시키지는 않았고 `needs_rate`로 남았다**는 보호는 구분한다.

개선 기준: 주기를 나타내는 표현이 있으나 정규화하지 못했다면 누적량으로 바꾸지 않는다. 일상적인 빈도를 지원하되 모호한 표현은 계산 보류로 표시한다.

### 8. 분수 개월 기간 정정 거절 — P2, 2개 실패 조건

KR-24: `기간은 두 달 반으로 늘릴게.`를 기존 월 환산 관례에 따라 약 11주로 정규화한 후보가 거절된다. `기간을 11주로 변경할게.`는 통과한다.

원인: `resolveGoalPeriod`가 기간 원문에서 정수 부분 ‘두 달’만 추출하여 정규화 후보와 불일치로 본다. 약 11주는 기존 52주/12개월 근사 기준이며 정확한 달력 마감일을 뜻하지 않는다.

개선 기준: 수치+단위+분수 부분을 함께 해석한다. 정확한 날짜가 필요한 경우 기간 근사와 달력 마감을 구분한다.

### 9. 가용 시간 0분인데 중간 준비 판정은 `ready` — P2, 1개 실패 조건

KR-25: 현재 매주 1편, 목표 4주에 4편인 상태에서 `주당 0분 가능해.`를 저장해도 `assessGoalFeasibility`는 `ready`로 남는다. 시간 상태가 `known`인지만 보고 실제 0분인지는 판정에 반영하지 않기 때문이다.

**추가 대조:** 동일 상태에 주 10분의 초안 계산 입력을 주면 최종 `goalFeasibilityIssue`는 `goal_capacity_conflict: 확인한 주간 한도 0분보다 초안 10분이 큽니다.`로 차단했다. 따라서 “0분인데 실행 계획이 실제로 확정됐다”는 결론은 내리지 않는다.

개선 기준: 중간 현실성 판정과 최종 초안 검증이 같은 실행 여건 제약을 사용해야 한다. 불필요한 초안 생성·재시도를 앞단에서 예방한다.

### 10. 마감 날짜 원문과 정규화 값 불일치 허용 — P1, 5개 실패 조건

US-19: 사용자 원문은 `November 30, 2026`인데 후보의 `normalized`를 `2026-12-31`로 보내면 12월 31일·15주로 저장한다. 실제 에이전트 기록 경계도 같다. 올바른 `2026-11-30` 대조군은 현지 날짜 기준 11주로 저장한다.

원인: 기간 수치는 원문과 교차 확인하지만 `resolveGoalPeriod`의 마감 분기는 유효한 미래 날짜인지만 확인하고 원문 날짜와의 일치를 확인하지 않는다.

개선 기준: 명확한 달력 날짜는 결정적인 파서로 교차 확인한다. 원문과 구조화 값이 다르면 저장하지 않는다. 날짜 순서가 지역별로 모호한 입력은 확정하지 않는다.

### 11. 목표 복원 시 지운 세부 내용까지 재주입 가능 — P2, 3개 실패 조건

US-20: 독서 분야를 제외한 후 `Restore reading. I have not decided the details again yet.`라고 말했을 때, 복원 명령과 과거 수준·목표 후보를 함께 저장 함수에 보내면 0권·2권 목표가 다시 살아난다. 분야만 복원하는 대조군은 수준·목표가 비어 있어 정상이다.

원인: 복원 뒤 빈 필드에는 과거 대화 근거로 채울 수 있다는 일반 규칙이 적용되어, 제거했던 세부 내용의 부활까지 허용한다.

**중요한 보호:** 이번 실제 에이전트 경로는 새로 복원하는 분야의 과거 세부 후보를 먼저 걸러냈고 분야만 복원하여 통과했다. 현재 보이는 오류는 **하위 저장 함수의 방어 일관성 공백**이다. 운영 경로에서 같은 부활이 관측됐다고 주장하지 않는다.

개선 기준: 새 분야의 빠진 정보 보충과 삭제 후 복원의 재동의를 구분하고, 동일 규칙을 최종 저장 함수에도 적용한다.

## 보완 순서 제안 — 이번에는 구현하지 않음

1. **변경의 의미 검증 통일:** 거절·조건부·인용·본인/타인·과거/현재·확정을 공통 구조로 다룬다. 현재 발언에 원문이 포함된다는 사실만으로 저장을 승인하지 않는다.
2. **필드마다 다른 검증 정리:** 목표·현재 수준·가용 시간·기간·목표 제외에 같은 근거 범위 규칙을 사용한다. 에이전트 사전 필터와 최종 저장의 차이도 줄인다.
3. **결정적인 계산 강화:** 날짜 원문 검증, 기간·빈도 정규화, 알 수 없는 빈도와 누적량 구분, 0분 제약을 공통화한다.
4. **수정 후 이번 705개를 동결 회귀에 추가:** 원문·기대값을 유지하고 긍정/부정 대조를 재검사한다. 그 뒤 예산을 정한 실제 모델 평가로 추출 품질을 확인한다.

이 방향은 모델 호출을 매 턴 하나 더 추가하는 안이 아니다. 구조화된 판단을 쓰더라도 현재 요청 안의 후보 설계와 로컬 검증을 우선한다. 이번 진단만으로 모델 교체나 품질 저하를 결론내리지 않는다.
