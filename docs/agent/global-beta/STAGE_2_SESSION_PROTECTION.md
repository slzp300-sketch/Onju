# 2단계 — 익명 세션 소유권 보호

작성: 2026-09-15 / 범위: 로컬 구현·오프라인 검증. 운영 적용 아님.

## 보호 계약

- UUID는 대화 식별자일 뿐이다. 별도로 생성한 32바이트 난수 토큰이 있어야 읽기·쓰기가 가능하다.
- 브라우저는 ID와 토큰을 한 쌍으로 저장한다. 요청을 만들 때 화면이 처음 읽은 ID와 현재 저장된 쌍이 같은지 검사한다.
- 서버는 토큰 원문 대신 SHA-256 해시로 소유권 RPC를 호출한다. RPC 오류·알 수 없는 결과에서 인증을 생략하지 않는다.
- 실제 로그인 계정 인증을 추가한 것은 아니다. 이 토큰을 가진 브라우저가 소유자다. 동일 브라우저 프로필 공유, XSS, 기기 탈취를 방어하는 계정 인증의 대체재로 표현하지 않는다.

| 상황 | 처리 |
| --- | --- |
| 처음 생성한 UUID·유효한 토큰 | 원자적 생성 후 접근 허용 |
| 이미 존재하는 UUID·다른 토큰 | 403, 기존 데이터 반환·변경 안 함 |
| 기존 UUID에 저장된 소유 해시가 없음 | 403, 소유권 자동 선점·자동 이전 금지 |
| 만료된 소유 세션 | 410, 다시 살려서 읽거나 갱신하지 않음; 소유자는 삭제 가능 |
| 삭제된 세션 | 410, 삭제 표식으로 같은 ID의 재생성 차단 |
| 다른 탭에서 새 대화 시작 | 이전 화면의 요청·캐시 쓰기를 거부/중단 |
| 소유하지 않은 이전 공급자 응답 ID | 403, 모델 요청 전에 거부 |
| 소유권 RPC 장애 | 일반 실패 처리, UUID만으로 진행하지 않음 |

구조화된 요청 ID/멱등성은 주 대화의 기존 turnId를 보존했다. 모든 유료 경로의 요청 중복 방지는 다음 3단계의 범위다.

## 변경 위치

루트와 별도 사이트 작업본에 같은 공통 보호를 적용했다. 사이트 작업본 전체를 루트로 복사하거나, 기존 모델·프롬프트·평가 설정을 덮어쓰지 않았다.

- 공통 서버: `_shared/webMvpAccess.ts`, `_shared/webMvpResponseOwner.ts`.
- 루트 진입점: `onju-agent-v2`, `onju-memory`, `onju-plan-agent`, `onju-daily`, `onju-plan-revision-agent`, 구형 `onju-agent`, `onju-goal-agent`.
- 사이트 주요 진입점: 위 목록 중 존재하는 주요 5개와 `onju-telemetry`. 버전 wrapper와 평가 wrapper는 기존 주요 진입점을 import한다.
- 기존 앱 인증 경로 `interpret-schedule`, `send-reminders`는 변경하지 않았다.
- 브라우저: `agentSession.ts`, 요청 클라이언트, `ScheduleSetup`, 계획·오늘 화면, `model.ts`, 사이트의 `planPersistence`·`publicBetaSession`.

### 브라우저 오류·이전 정책

불러오기 실패를 “저장된 내용 없음”으로 간주하지 않는다. 저장·전송을 중단하고 재시도와 새 대화 시작을 제공한다. 입력은 대화별 로컬 임시 저장과 화면 상태에 남긴다. 저장소를 사용할 수 없는 경우에는 메모리만 유지되므로 새로고침 후 보존은 보장하지 않는다.

새 대화 시작과 이전 대화 삭제는 별개다. 소유 확인 실패 시 자동으로 새 ID를 만들고 기존 화면의 대화·목표를 복사하던 사이트 경로를 제거했다. 사용자가 확인한 새 대화에는 방금 입력한 문장만 옮기며 서버의 이전 기록은 삭제하지 않는다.

이전 토큰 없는 세션이나 소유 해시 없는 서버 기록은 안전하게 자동 복구할 근거가 없다. 기존 기록을 자동 삭제하지 않고, 새 대화 또는 검증 가능한 별도 복구 절차가 필요함을 알린다. 로컬 캐시는 세션별 키로 나누고 기존 비분리 캐시는 원래 세션에만 한 번 연결한다.

### 저장·삭제 경계

- 서버가 관리하기 시작한 대화(version 3 이상)는 늦게 도착한 화면 자동 저장으로 덮어쓰지 않는다.
- 계획 저장은 명시적인 저장 경로로 유지했다. 자동 저장을 막으면서 계획까지 사라지는 회귀를 검사했다.
- 삭제는 일반 세션 생성·갱신 RPC를 먼저 부르지 않는다. 전용 소유 확인·삭제 RPC를 사용한다.
- 삭제 확인 전에는 성공으로 표시하지 않는다. 애매한 실패 뒤 일반 저장을 중단하고 동일 삭제 요청을 재시도할 수 있게 한다.
- 세션 삭제 트리거는 토큰 해시·UUID·삭제 시점만 남긴다. 늦은 세션 삽입과 자식 레코드 저장을 차단한다.
- 자식 쓰기는 실제 세션 FK 테이블에 트리거를 설치하고 부모 key-share 잠금으로 삭제와 조정한다.
- 이전 모델 응답을 이어받는 구형 경로·계획 수정 경로에는 서버가 기록한 `response_id → session_id` 소유 목록을 추가했다. 클라이언트가 저장 필드에 응답 ID를 적는 것만으로 소유 목록을 만들 수 없다.

삭제 범위는 세션 행과 실제 FK cascade로 연결된 자료다. 공급자 저장 응답, 백업, 비연결 사용량 집계, 삭제 표식까지 모두 즉시 지운다고 약속하지 않는다. 삭제 표식 보관 기간과 전체 데이터 안내는 5단계 및 게시 전 확인 대상이다.

## SQL 검증과 적용 전 조건

새 마이그레이션: `202609150001_web_mvp_session_ownership.sql`.

별도 사이트 작업본의 웹 스키마 0007~0034를 빈 PostgreSQL/WASM(PGlite 0.5.8) DB에 실행한 뒤 새 마이그레이션을 실행했다. 생성·소유자 불일치·만료·기존 무소유 행·삭제·재생성·자식 이동·권한을 실제 SQL로 검증한다. 새 자료는 모두 합성값이며 DB는 메모리에만 존재한다.

이는 운영 DB 복사나 두 저장소의 마이그레이션 이력 통합 완료가 아니다. 실제 운영 스키마, 서버 설정, 인증 헤더, 여러 연결의 경쟁 조건은 별도로 확인해야 한다. PGlite 동시 요청 검사는 단일 엔진의 대기열이며 다중 연결 동시성 검증으로 계산하지 않는다.

적용 전 필수 조건:

1. 1단계에서 확인한 양쪽 migration ledger 충돌과 운영 스키마를 대조한다. 기존 SQL을 교체하거나 번호만 바꿔 중복 적용하지 않는다.
2. 통합 대상 기본 테이블을 준비한 뒤 새 보호 SQL을 적용한다. 이후 새 세션 FK 테이블에도 쓰기 트리거를 설치한다.
3. 기본 역할·RLS·RPC 실행 권한·소유 해시 형식·만료 시각을 별도 검증 환경에서 재확인한다.
4. 클라이언트, 주요 서버, wrapper, 캐시의 적용 순서를 묶어서 검토한다. 구형 UUID-only 쓰기와 토큰 없는 insert/upsert는 의도적으로 실패한다.
5. 기존 소유권 미확인 세션과 공급자 응답 ID는 자동으로 신뢰하지 않는다. 사용자 복구·새 대화 안내를 함께 준비한다.
6. 보호 SQL만 적용하고 구형 서버를 오래 남겨 두지 않는다. 복구 시에도 UUID-only 접근이나 만료 갱신을 되살리지 않는다. 검증 전 운영 적용은 보류한다.

## 반복 검증 방법

저장소 루트에서 테스트 전용 패키지 설치: `npm ci --prefix web-mvp/qa/session-db --ignore-scripts`.

설치 후 `web-mvp`에서 `npm run test:session` 또는 `npm run verify:offline`.

- 테스트 패키지는 웹 실행 의존성에 추가하지 않았다. QA 전용 manifest·lockfile로 버전을 고정했다.
- 전체 검사에는 루트·사이트 스크립트, 앱 단위 검사, React DOM 복구 검사, 양쪽 타입·빌드, 루트 ESLint·knip가 포함된다.
- 사이트의 실제 모델 평가 명령은 실행하지 않는다. 기존 `test:agent`에 명시된 로컬 테스트만 실행한다.
- 외부 네트워크 차단을 적용한다. PostgreSQL 엔진의 SQL 실행도 로컬 메모리에서 끝난다.
- 시각적 390px 브라우저 QA, 독립 PostgreSQL 연결 경쟁 시험, 운영 API 검증은 통합/배포 전 검증 항목으로 남는다.
