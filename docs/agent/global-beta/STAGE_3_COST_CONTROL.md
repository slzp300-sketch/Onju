# 3단계 — 비용·중복 호출·실패 처리 계약

2026-09-15 · 로컬 개발/오프라인 검증 · 운영 적용 없음

## 범위

원본 앱을 유지하면서 루트 웹 MVP(A)와 사이트 작업본(C)에 같은 비용 보호를 적용했다. C의 모델 선택, Gemini/혼합/캐시 평가 분리 및 기존 기능은 보존했다. B(사이트 기준 커밋)는 수정하지 않았다.

| 경로 | 루트 A | 사이트 C | 보호 지점 |
| --- | --- | --- | --- |
| 주 대화 및 보조 판단·검색 | `onju-agent-v2` | `onju-agent-v2` | 소유권 → 요청 횟수 → 모델별 비용 예약 → 응답/정산 → 기존 상태 저장 |
| 주간 계획·검증 후 재생성 | `onju-plan-agent` | 동일 | 각 논리 호출을 공통 보호로 실행 |
| 계획 수정·이전 응답 포인터 처리 | `onju-plan-revision-agent` | 동일 | 포인터 소유 확인 후 예약; 400 거절만 포인터 없는 재요청 허용 |
| 주간 회고·선택적 일일 조정 | `onju-daily` | 동일 | `requestModel` 내부의 모든 공급자 시도를 보호; 적용 날짜를 요청 식별에 포함 |
| 이전 일정/목표 대화 | `onju-agent`, `onju-goal-agent` | 기존 별칭이 주 대화 진입점 재사용 | A의 직접 HTTP 호출도 공통 보호 적용 |
| 인증된 공급자 평가 | 활성 평가 진입점 없음 | OpenAI/Gemini/hybrid/cache 평가 별칭 | 기존 인증 유지; 평가 함수 이름으로 식별 분리; evaluation 예산 |

원본 앱의 별도 인증을 사용하는 `interpret-schedule`은 웹 MVP 범위가 아니므로 변경하지 않았다. Supabase/저장/분석 요청을 모델 호출로 계산하지 않는다. 미사용 평가 어댑터 유틸리티는 활성 HTTP 경로와 구분한다.

## 저장 및 호출 계약

신규 공통 모듈: `supabase/functions/_shared/webMvpCostControl.ts` (A/C 동일).

신규 SQL: `supabase/migrations/202609150002_web_mvp_cost_control.sql` (A/C 동일).

- `web_mvp_ai_calls`: 세션·공개/평가 범위·논리 호출 키, 원래 예산 날짜, 예약액, 현재 반영액, 관측 비용, 상태, 복구용 공급자 응답.
- `web_mvp_ai_cost_days`: 날짜·범위별 총 반영액. 세션을 삭제해도 지출 한도를 되돌리지 않는다.
- `web_mvp_begin_ai_call`: 서버 시각 기준의 일일 예산, 세션 금액, 세션 호출 횟수를 한 트랜잭션에서 확인한다. 같은 범위의 예약·정산은 같은 advisory lock을 사용한다.
- `web_mvp_finish_ai_call`: 예약 ID로 한 번만 정산한다. 자정 이후 도착해도 예약했던 날짜에 반영한다.
- 원래 대화 데이터의 상태 저장/CAS를 대체하지 않는다. **모델 호출의 중복 방지와 모든 제품 동작의 exactly-once 처리는 다른 문제다.**

| 결과 | 처리 | 후속 동일 키 요청 |
| --- | --- | --- |
| 처리 중 | `reserved`, 예약액 유지 | 추가 호출 없이 처리 중 안내 |
| 성공·사용량 확인 | `completed`, 관측 토큰 비용 추정치로 정산 | 저장된 응답 재사용; 다시 과금하지 않음 |
| 성공·사용량/도구 비용 불명 | `completed`, `actual_microusd=null`, 예약액 유지 | 응답은 사용/복구 가능; 비용을 0으로 기록하지 않음 |
| 명시적인 HTTP 4xx 거절 | `rejected`, 보수적으로 예약액 유지 | 허용된 재시도는 새 예약 ID; 시도 횟수/비용 기록 보존 |
| 타임아웃·전송 오류·5xx 불명 | `unknown`, 예약액 유지 | 자동 재호출 차단; 운영 확인 필요 |
| 예약 저장소 장애 | 유료 호출 전 차단 | 복구 후 재시도 가능 |
| 정산 저장소 장애 | 미정산 예약 유지, 미저장 결과를 성공으로 넘기지 않음 | 재과금 금지; 오래된 예약도 자동 해제하지 않음 |

`reserved`가 3분을 넘기면 재호출 대신 처리 결과 불명으로 안내한다. 이는 예약을 해제하거나 결과를 자동 확정한다는 뜻이 아니다. 운영자가 공급자 기록과 대사하기 전에는 불명 비용을 0으로 바꾸지 않는다.

재시도 중 429 → 성공은 같은 논리 호출 번호를 사용한다. 성공한 뒤에만 번호를 증가시켜, 응답 유실 후 처음부터 재전송해도 앞선 성공 결과를 재사용한다. 상위 에이전트가 예외를 잡고 다시 모델을 부르려 해도 비용 차단 상태를 우회할 수 없다.

브라우저는 대화 전송 중 동기적인 ref 잠금으로 더블 클릭을 막고, 재시도에는 기존 `turnId`를 사용한다. 계획 생성 재시도에서 매번 새 UUID를 만드는 동작도 없앴다. 명시적 요청 ID가 없는 기존 경로는 정렬된 요청 내용의 해시를 사용한다. 토큰은 해시 대상이나 복구 응답에 복사하지 않는다.

제한: 별개의 새 요청 ID를 발급한 요청을 무조건 같은 사용자 의도로 판정하지는 않는다. 익명 새 세션을 계속 만드는 공격도 주소 하나로 해결하지 않는다. 세션 한도와 전체 예산을 함께 적용한다. 같은 입력·계획 맥락의 재생성은 저장 응답을 재사용할 수 있다; 다른 초안을 의도적으로 요청하려면 입력/계획 맥락이 달라야 한다.

금액 0은 명시적 중지다. 잘못된 값/음수/100달러 초과를 자동으로 5달러로 바꾸지 않고 설정 오류로 차단한다. public와 evaluation 예산은 독립적이다; 둘의 합이 서비스 전체 최대 허용액인지 운영자가 별도로 결정해야 한다. 기존 표면별 요청 횟수 제한도 유지하며, 루트의 이전 대화 경로에 누락된 제한을 추가했다.

주소 제한은 프록시가 헤더를 덮어쓰고 우회 접속이 차단됨을 확인한 뒤에만 활성화한다. 클라이언트가 보낸 첫 X-Forwarded-For 값을 신뢰하지 않는다. 미확인 주소를 모두 `unknown` 버킷 하나에 넣어 정상 사용자를 함께 제한하지 않는다.

## 가격·품질·재시도

- 모델·프롬프트·출력 토큰 제한·온주 판단 규칙은 비용 절감 목적으로 바꾸지 않았다.
- 모델 이름/날짜 스냅샷을 정확하게 구분한다. `gpt-4.1-mini`를 `gpt-4.1` 가격으로 계산하던 접두사 문제를 수정했다.
- 알려지지 않은 모델은 임의의 저렴한 단가로 호출하지 않고 가격 확인이 필요하다고 차단한다.
- 캐시 읽기/쓰기 비용을 보존하고, Gemini 사용량 자체가 없는 응답을 0토큰으로 변환하지 않는다.
- 기존 이벤트 요약도 사용량·가격 누락 시 총액을 `null/incomplete`로 기록한다. `known_token_cost_usd`는 확인 가능한 부분 합계일 뿐 총 청구액이 아니다.
- 검색 등 도구 비용은 토큰 사용량만으로 모두 확인할 수 없어 예약액을 유지한다. 이전 response ID의 숨은 입력 문맥, 가격/티어 변화 등으로 실제 청구액이 예약을 초과할 수 있다. **앱의 추정 예산은 공급자 청구 상한 보장이 아니다.**
- Retry-After의 초/날짜/밀리초를 최소 대기로 취급한다. 12초를 넘는 서버 대기를 12초로 줄여 다시 호출하지 않고 사용자에게 미룬다. 키/결제/할당량 조치가 필요한 오류를 자동 반복하지 않는다.
- 타임아웃/5xx에서 자동으로 다른 모델을 다시 호출하던 동작은 중복 과금 방지를 위해 중지한다. 이 선택은 불명확한 장애에서 자동 복구보다 비용 안전을 우선한다. 실제 자연어 품질이나 모든 장애 복구 성공률이 동일하다는 검증은 아직 하지 않았다.

공식 근거: [OpenAI rate limits](https://developers.openai.com/api/docs/guides/rate-limits) — 실패 요청도 요청 제한에 기여하며, Retry-After보다 빨리 재시도하지 않고 billing/quota 오류를 반복하지 않도록 안내한다. [GPT-4.1 mini](https://developers.openai.com/api/docs/models/gpt-4.1-mini) — 1M 토큰당 입력 $0.40/캐시 입력 $0.10/출력 $1.60을 확인했다. 다른 기존 모델 단가는 이번에 일괄 갱신한 것이 아니며 운영 전 가격/계약 확인이 필요하다.

## 두 번의 점검

1차: 양쪽 활성 호출 경로/별칭/검색/보조 판단/회고/재생성을 목록화했다. 원본 앱과 웹 MVP, 공개 요청과 인증 평가를 구분했다. 금액만 반환하는 기존 예약 코드의 중복 정산·자정·실패 0원 문제를 확인했다.

2차: 실제 수정 후 추가로 발견한 항목을 보완했다.

- 429 다음 성공의 재사용, 상위 catch에서 비용 차단 우회 방지.
- 평가 함수 간 복구 키 분리와 일일 기록 날짜 분리.
- 명시적 예산 0/잘못된 설정, first-use rate bucket 경쟁.
- Gemini 사용량 누락, mini 모델 접두사 가격 오류.
- 비용 오류가 화면에서 연결 오류로 바뀌는 문제, 같은 프레임의 더블 클릭.
- 구형 금액 단위 예산 RPC의 실행 권한을 차단해 신/구 대장이 동시에 증가하지 않게 함.

검증 코드는 `web-mvp/scripts/cost-control.test.mjs`, `web-mvp/qa/edge-handler-harness.mjs`, `web-mvp/qa/session-ui/setup-recovery.test.tsx` 및 C의 public-beta/gateway/telemetry/pilot-readiness 테스트다. 기존의 ‘실패는 0원 정산’, ‘타임아웃 후 자동 모델 재호출’ 기대값은 새 계약으로 교체했으며 나머지 기능 검사를 유지했다.

## 데이터 및 출시 전 조건

- 복구용 응답은 새 민감 데이터 저장소다. RLS + service-role 전용이며 세션 FK 삭제에 함께 삭제된다. 익명 토큰이나 원문 요청 body를 대장에 별도 저장하지 않는다.
- 세션 삭제 후 전역 일별 합계는 보존한다. 상세 응답과 세션 연결이 사라져도 서비스 한도가 되돌아가면 안 되기 때문이다.
- 익명 세션 생성/만료/삭제의 전제는 2단계 계약을 따른다. 이미 만료/삭제된 세션에는 예약이나 캐시를 다시 붙일 수 없다.
- 선택적 일일 조정의 AI 실패 시 기존의 결정적 축소 행동을 유지하는 동작은 보존했다. 모든 일일 기록 실패로 확대하지 않는다. 비용 대장에 불명/예약 상태는 남는다. AI/비AI 조정 출처를 안내하는 UX는 출시 전 안내 범위에서 재확인한다.
- 로컬 PostgreSQL/WASM(PGlite)은 실제 SQL을 실행하지만 쿼리를 한 엔진에 직렬화한다. **독립 DB 연결의 락 타이밍/부하 검증을 대신하지 않는다.**
- 390px 실제 브라우저, 원격 Supabase, 공급자 장애의 실제 과금, 영어 대화 품질은 이번에 검사하지 않았다.

### 적용 순서 — 아직 실행하지 않음

1. 1단계에서 발견한 루트/사이트 migration 이력을 실제 운영 ledger와 대조한다. 번호 충돌이 있는 과거 SQL을 그대로 복사하지 않는다.
2. 신규 AI 유입을 일시 중지하고 기존 호출·정산을 drain한다. 운영 예산, 프록시 신뢰 헤더, 세션 한도를 승인받는다.
3. 2단계 세션 migration 이후 3단계 SQL을 적용한다. 이전 일별 actual+pending을 신규 대장으로 이월한다. 과거 SQL 정의는 보존하되 구형 금액 단위 RPC 실행을 차단한다.
4. 모든 활성 서버 경로와 프런트를 맞춰 전환한다. 이전 함수/공개 별칭/캐시된 클라이언트가 우회할 수 없는지 확인한다.
5. 승인된 작은 예산으로 live 검증 후 점진적으로 연다. 이번 단계에서는 수행하지 않았다.
6. 롤백은 신규 호출을 중지한 뒤 양쪽 비용 대사를 먼저 수행한다. 구형 RPC 권한만 복구하거나 신규 대장을 삭제해 한도를 초기화하지 않는다.

불명 비용을 해제할 자동 타이머/자동 0원 정산은 없다. 운영 대사/복구가 필요한 건은 별도 승인 후 처리한다. 다음 4단계는 언어·국가·시간대·주 시작일의 일관성이다.
