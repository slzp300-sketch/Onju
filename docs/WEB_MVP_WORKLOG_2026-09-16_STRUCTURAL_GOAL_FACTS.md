# 온주 — 목표 사실·실행 제약의 구조 개선

작성: 2026-09-16 · 요청: “구조적인 문제를 먼저 해결하자”

후속 상태: 아래는 구조 개선 당시 기록이다. 이후 [남은 실행 여건 표현 보완](WEB_MVP_WORKLOG_2026-09-16_REMAINING_CAPACITY_LANGUAGE.md)에서 나머지 4유형·22개 실패 조건도 통과로 바뀌었다. 원래 진단 입력·기대값은 유지했으며, 최신 검증 근거와 지원 경계는 후속 작업로그에 기록한다.

## 범위와 결론

이번 범위는 **목표 정보가 저장되고 실행안에 적용되는 구조**다. 새로운 가상 사용자를 계속 추가하거나 질문 문구를 추가하는 방식 대신, 근거가 연결된 사실과 실행 제한을 별도로 보존하고 공통 검증 경계에서 사용하도록 수정했다.

수정 대상은 `logs/sites/onju-web-mvp/supabase/functions/onju-agent-v2/`의 Site 제품이다. 루트 앱과 루트 Edge Function의 기존 미커밋 변경은 건드리지 않았다. 배포·운영 DB 변경·커밋·푸시·노션 등록은 하지 않았다.

10차 진단의 6개 구조 유형에 해당하는 44개 실패 조건이 통과로 바뀌었다. 4개 표현 지원 유형의 22개 실패 조건은 남아 있다. **모든 문제 해결이나 실제 모델의 대화 품질 향상을 증명한 결과는 아니다.**

## 이전에 같은 종류의 문제가 반복된 이유

1. 원문에 같은 숫자가 있다는 것과, 그 숫자가 해당 사용자의 해당 목표에 대한 현재 실적이라는 것이 분리되지 않았다.
2. 사람이 읽는 시간 요약을 실행 제한으로도 사용해, 주간 합계만 남기고 하루 횟수·회당 시간이 사라질 수 있었다.
3. 최초 초안과 기존 계획 수정·승인의 검증 경계가 달랐다.
4. 가상 프로필 수, 작성된 후보에 대한 단언 수, 실제 모델 품질 검증을 같은 지표로 볼 수 없었다. 입력 변형에 대한 불변성 검사와 명확한 완료 범위가 필요했다.

## 바꾼 구조

사용자 발언 → 모델의 구조화 후보 → 근거·관계 검증 → 사실/실행 제약 저장 → 초안·수정·승인의 공통 제한 검사.

### 1. 사실의 관계를 함께 저장

`GoalFactBinding`은 필드 종류, 목표 분야, 값, 원문 인용, 관련 원문 범위, 주체, 시점, 완료 상태, 비교 가능한 수량을 분리한다.

- 원문에서 코딩에 속한 실적을 디자인에 저장하지 않는다.
- 완료·진행 중·목표량을 구분한다. 진행 중이라고 명시된 현재 상태 자체는 보존하지만 완료량으로 빼지 않는다.
- 부부 합산 시간과 개인의 시간을 구분한다. 공동 계획 기능 전체를 구현한 것은 아니다.
- 예상되는 미래 여유를 현재 확보한 시간으로 저장하지 않는다.
- 시간이 미측정인데 다른 문장의 프로젝트 번호를 근거로 시간을 만들지 않는다.
- 모델이 임의로 붙인 `binding` 값은 믿지 않고 저장 경계에서 다시 만든다.
- 반복된 동일 인용은 마지막 등장 위치만 보지 않는다. 목표 이름·문장 순서·수치가 바뀌어도 목표 연결이 유지되는지 검사한다.

`goalAreaIdentity`는 기존 분야 별칭 정의를 공유한다. 분야 별칭이 여러 활성 목표에 걸치면 한 목표라고 임의로 결정하지 않는다. 이는 제한된 언어 어댑터이며 모든 별명·대명사·문장 관계를 이해하는 의미 추론기를 완성한 것이 아니다.

### 2. 표시 요약과 실행 제한 분리

`GoalCapacityContract`에는 읽기 쉬운 요약과 별도로 원래 실행 여건의 근거 및 계산된 제한을 남긴다.

예를 들어 “평일 하루 두 번, 회당 10분”이 “주 100분”으로 요약되어도 아래 제한은 사라지지 않는다.

- 주간 최대 100분
- 주간 최대 10회
- 회당 최대 10분
- 평일 하루 최대 2회, 주말 배치 제외

저장 후 다시 불러와도 원문에서 제한을 재계산한다. 캐시된 숫자 한도를 임의로 크게 바꿔도 그것을 실행 권한으로 사용하지 않는다. 요약과 계약의 연결이 맞지 않으면 미해석 상태로 차단한다. 원문까지 외부에서 위변조하는 경우에 대한 암호학적 무결성 기능은 아니다.

기존 데이터는 새 필드가 없어도 읽힌다. 옛 기록에 원문 제한이 남아 있으면 우선 사용하며, 그렇지 않은 기존 요약은 종전 해석 경로를 유지한다. 예전 기록에서 이미 사라진 원문을 복원했다고 주장하지 않는다. 마이그레이션이나 운영 DB 변경은 없다.

수치가 다른 현재 실적과 시간 예산이 한 문장에 있으면 분리한다. 반대로 같은 시간 예산에 붙은 요일 예외를 짧은 인용 밖이라고 제거하지 않는다. 해석하지 못한 제한을 임의로 무시하지 않는다.

### 3. 동일한 제한을 생성·수정·승인에 적용

`goalCapacityIssue`를 초기 초안, 기존 목표 수정, 저장된 초안 승인에 공유한다.

- 첫 초안이 통과했더라도 수정으로 회당 한도를 넘길 수 없다.
- 기본 수정안뿐 아니라 함께 제시되는 연관 수정안도 검사한다.
- 오래된 초안이 현재 한도를 넘으면 승인 버튼만으로 확정하지 않는다. 충돌 정보를 모델에 전달해 설명·수정 대화로 이어간다.
- 실제 가용 시간이 바뀌었다고 이번 발언에서 명시한 경우에만 `revise_goal.capacity_update`로 새 여건을 함께 검증한다. 단순히 행동 시간을 늘려 달라는 말은 새 가용 시간의 근거가 아니다.
- 수정안은 여전히 미확정이다. 확인된 목표를 바로 덮어쓰지 않으며 새 승인이 필요하다.
- 저장·수정 검증 실패 시 입력 상태와 확정 목표는 보존한다.

### 4. 대화 내용과 검증 정책 분리

새 바인딩·제약 객체에 고정 답변, 필수 질문 순서, 선택 버튼을 넣지 않았다. 모델은 최근 대화에 따라 답변하고, 코드가 후보 정보와 실행 한도의 일관성을 검사한다.

모델의 매 턴 동적 입력에는 중복된 바인딩·원문 묶음을 그대로 반복하지 않고 정리된 사실과 실행 제한을 전달한다. 실제 토큰 비용 감소량은 측정하지 않았다. 수집 도구 결과 등에는 호환성을 위해 상세 데이터가 남는다.

모델 종류·공급자·추론 설정을 바꾸거나 모델을 재학습한 작업은 아니다. 기존 대화 흐름의 모든 규칙을 제거한 것도 아니다.

### 수정 중 발견·해결한 회귀

- 최초 전체 검사에서 바인딩 주체의 TypeScript 타입 추론 오류, 기존 분야 별칭 과잉 차단, 현재 실적의 월간 빈도가 시간 예산에 섞이는 문제를 발견했다. 기존 기대값을 바꾸지 않고 제품 코드를 수정했다.
- 옛 데이터에도 미해석 제한을 적용하는 과정에서 영어 요일 목록의 마지막 쉼표가 문장 경계로 잘리는 문제가 드러났다. 기존 요일 인식기를 근거 구분과 공유하고, 새 저장·재로딩 검사도 추가했다.
- 오래된 승인 경로의 제한 충돌이 모델 입력에서 제거되던 화이트리스트도 보완했다.
- 실패 이력은 `logs/offline-development/2026-09-16T07-23-04-773Z/`, `2026-09-16T07-41-25-423Z/`, `2026-09-16T07-43-20-479Z/`에 보존했다.
- 10차 입력 파일·실행 도구 및 기존 1~9차 기대값을 수정해 통과시킨 것이 아니다.

### 변경 파일

제품 경로 `logs/sites/onju-web-mvp/supabase/functions/onju-agent-v2/`:

- `goalFactBinding.ts` 신규: 사실의 목표·주체·시점·완료 상태와 원문 연결.
- `goalCapacityContract.ts` 신규: 표시 요약과 독립적인 실행 제한, 재로딩·옛 데이터 처리.
- `goalAreaIdentity.ts` 신규: 기존 분야 별칭과 목표별 원문 위치의 공유 해석.
- `goalBrief.ts`: 최종 저장 경계와 간결한 모델 입력용 사실 뷰.
- `goalIntakeEvidence.ts`: 시간 후보의 단위·측정 근거, 정상 완료량 비교.
- `goalFeasibility.ts`: 진행 중 실적 보호 및 공통 실행 한도 검사.
- `agent.ts`: 생성·수정·승인 경로 연결, 근거가 있는 실행 여건 변경.
- `prompt.ts`: 미확정 초안의 한도 충돌을 모델에 전달.
- `goalDays.ts`, `goalEvidenceScope.ts`: 요일 목록을 한 사실의 범위로 유지.

별도 신규 검사 파일은 `web-mvp/scripts/goal-structure.test.mjs`다.
