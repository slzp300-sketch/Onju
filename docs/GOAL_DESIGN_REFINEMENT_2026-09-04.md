# 목표 수정 보호와 부담 조절 — 1·2단계

2026-09-04 · 한국시간 · GPT-4.1 유지

## 이번 범위

이전 [대화 품질 검증](AGENT_QUALITY_UPGRADE_2026-09-04.md)에서 남긴 두 문제를 개선했다. 요청하지 않은 목표 조건까지 변경하는 문제, 처음부터 과한 실행량을 제안하는 문제다. 실제 요일·시각에 루틴을 배치하는 다음 단계는 이번 범위가 아니다.

운영 `onju-agent-v2`와 로컬 웹에 반영했다. 기존 사용자 기록 삭제, DB 마이그레이션, Git 커밋·푸시, Notion 업로드, 웹 호스팅 재배포는 이번 작업에서 하지 않았다.

## 1. 원하는 부분만 수정

- 기존 목표를 통째로 다시 작성하는 대신 `revise_goal.edits`로 요청된 필드만 수정한다. 각 변경은 현재 사용자 발언의 원문 근거를 포함해야 한다.
- 횟수만/시간만 요청, 행동 인덱스, 잘못된 숫자, 중복 변경 등을 서버에서 검사한다. 모델이 보내지 않은 나머지 필드는 원본을 그대로 복사한다.
- 수정 초안에 **변경 전 → 변경 후**를 표시한다. 초안과 확정 목표를 계속 분리한다.
- 예: 독서를 주 3회에서 1회로 줄이면, 기간 2주·회당 10분·기존 결과 기준은 요청 초안에서 그대로 둔다. 2주간 6회라는 결과 기준이 맞지 않으면 2회로 조정하는 안을 별도로 보여준다.
- 결과 기준뿐 아니라 목표 문장에 들어 있는 명백한 기간·횟수, 행동 이름의 시간 표현도 연관 변경으로 확인한다. 관련 조건이 있는 상태의 단순 “응”은 확정하지 않는다. `관련 조건도 함께 조정할게요`라는 명확한 승인으로 해당 버전만 확정한다.
- 새로고침과 요청 재시도 시에도 초안 버전·변경 목록·관련 승인 모드를 유지한다. 승인은 모델 호출 없이 보던 카드를 그대로 저장한다.

## 2. 작은 실행량부터 제안

- 별도 요청이 없을 때의 시작 기준: 회당 15분 이하, 행동별 주 3회 이하, 전체 주 90분 이하. **연구로 입증된 최적량이 아니라 조절 가능한 제품 기본값**이다.
- 하루 10분, 주당 30분 같은 명시적 시간 한도와 알려진 요일의 빈 시간을 반영한다. 미정인 요일을 가용 시간으로 만들어 넣지 않는다.
- 주간 합계뿐 아니라 하루 한도에 각 실행을 나누어 넣을 수 있는지도 검사한다. 예를 들어 평일 5일 × 하루 10분에는 8분짜리 실행 6회를 넣을 수 없다.
- 사용자가 명확히 요청한 주 3회 × 60분 운동은 알려진 여건이 허용하면 유지한다. 모든 목표를 무조건 15분으로 줄이는 방식은 아니다.
- 바쁜 날 최소 실행을 초안에 포함하고, 주간 총 실행 시간을 표시한다. 생활 리듬이 미정이거나 빈 시간이 없으면 실제 배치 가능 여부를 아직 확인하지 못했다고 알린다.
- 사용자가 정확한 종료 날짜를 주지 않았다면 임의 날짜를 넣지 않고 시험 기간만 제안한다.
- 새 초안의 목표 문장에서 “매일”, “각각 주 5회”라고 하면서 실제 행동은 주 2·2·1회인 명백한 불일치도 검사한다. 목표 문장은 원하는 변화, 실행 숫자는 주간 행동 필드에 두도록 안내한다.

OpenAI Docs의 [함수 호출 가이드](https://developers.openai.com/api/docs/guides/function-calling)를 참고해, 모델은 제안과 요청 해석을 담당하고 알려진 데이터의 보존·수치 검사·승인은 코드가 담당하도록 구성했다. 파인튜닝이나 ChatGPT 비공개 데이터 학습을 한 것은 아니다.

## 검증 방법과 중간 발견

- 단위/회귀 테스트: 에이전트 42개 통과. 텍스트·스크롤 Vitest 10개 통과.
- 웹 production build와 에이전트 코어 TypeScript 검사 통과.
- 실제 API: 기존 9개 사례 + 목표 설계 6개 사례. 고정 GPT-4.1 스냅샷, 합성 상태, KST 기준, 사용자 DB 접근 없는 임시 함수로 실행했다.
- 새 6개 사례는 특정 행동의 횟수만 수정, 연관 결과 기준의 별도 승인, 시간만 수정, 하루 10분 한도, 피곤한 사용자의 작은 시작, 명시한 긴 운동 유지다.
- 첫 실행은 자동 검사 14/15였다. `three-goals`의 신앙 관련 표현이 문자 그대로 “신앙”을 포함하지 않아 실패했고, 원문에는 말씀·기도가 있었다. 이 실패 기록을 지우지 않았다.
- 두 번째 실행은 자동 검사 15/15였지만, 원문에서 하루별로 배치 불가능한 8분 × 6회와 임의 종료 날짜를 발견해 검사와 코드를 보완했다.
- 세 번째 실행도 자동 검사 15/15였으나, 목표 문장에 “각각 주당 5회”, “매일”을 쓰고 실제 횟수는 다르게 제안했다. 목표 문장 검사와 사례를 추가했다. 하루 10분 사례는 내부 수정 3회로 12.36초·4회 모델 호출이 들었다.
- 따라서 자동 통과율은 전체 AI 품질이나 자연어 의미 일관성 100%를 뜻하지 않는다. 매번 응답 원문을 함께 읽었다. 검사 강화 전후 실행은 동일한 평가 기준이 아니므로 단순 통과율 개선이나 비용 절감으로 해석하지 않는다.

중간 결과는 `docs/evals/agent-goal-design-<실행 ID>.json`으로 보존한다.

## 남은 한계 / 다음 단계

- 요청 근거와 숫자 해석에는 제한된 한국어 패턴을 사용한다. 숫자 한글 표기, 복잡한 부정, 여러 분야별 서로 다른 예산, 긴 대화의 조건 철회는 추가 검증이 필요하다.
- 기존 카드의 행동 추가·삭제, 목표 전체 교체는 현재 부분 수정 도구가 지원하지 않는다. 확인 질문을 할 수는 있어도 이 기능이 완성됐다는 뜻은 아니다.
- 기존 목표의 요청하지 않은 문구나 최소 실행은 그대로 보존한다. 테스트의 복수 분야 카드에 있던 독서용 최소 실행도 의도적으로 유지했으며, 이것이 해당 분야에 적절하다고 평가한 것은 아니다.
- 연관 조건 수정은 인식 가능한 기간·횟수·행동 이름 관계에 한정한다. 임의 자연어 결과 기준 전체의 의미를 증명하지 않는다. 새 초안의 문장 검사는 기존 목표 문장을 자동 재작성하지 않는다.
- 종료 날짜는 현재 사용자 원문에 정확히 같은 문자열이 있을 때 보존한다. “9월 말까지” 같은 표현을 날짜로 정규화하는 작업은 남았다.
- 일별 검사는 가용 분량과 선호 요일 기준이다. 실제 시작/종료 시각, 분절된 여러 빈 구간에 모든 루틴이 들어가는지, 이동·휴식 여유까지 검증하는 완성된 주간 스케줄러가 아니다. 탐색 한도를 넘기면 불명확으로 취급한다.
- 부담 한도는 새 초안 생성에 적용한다. 기존 목표의 부분 수정에서 요청하지 않은 실행량까지 강제로 줄이지 않는다.
- 모델이 수정 요청을 여러 번 받으면 응답 지연과 비용이 늘어난다. 최종 검증 사례 외 장기 대화·다중 사용자·완주율을 입증하지 않았다.
- 다중 Supabase 클라이언트 경고는 이전부터 관찰됐으며 별도 정리 대상이다. 공개 고객 테스트 전 세션 보호·속도/비용 제한·관측도 별도 점검해야 한다.

**다음 3단계:** 확정 목표의 실행 횟수와 시간을 시간 지도에 배치하고, 고정 일정·수면·휴식과 충돌하지 않는지 검사한 뒤 주간 계획으로 제안한다.

## 정리

- 임시 평가 함수는 난수 토큰과 2시간 만료를 적용했고 토큰 없는 요청의 403을 확인했다. JWT 검증 해제 옵션은 사용하지 않았다.
- 원격 임시 함수, 로컬 생성 함수 폴더와 임시 토큰 파일은 삭제했다. 필요하면 검증 실행기의 `prepare --suite=goal-design`으로 새 토큰/함수를 재생성할 수 있다. 원시 응답과 실행 이력은 보존했다.
- 기존 5173 `/setup` HTTP 200 확인. 사용자 원래 브라우저 탭은 건드리지 않았다.
