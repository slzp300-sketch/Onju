# 온주 — 8차 가상 사용자 20명 진단

작성: 2026-09-16 · 요청: “다시 20명의 가상 이용자를 추가로 넣어서 검증해보자”

후속 상태: 사용자 승인 후 8개 유형의 로컬 보완과 재검증을 완료했다. 원본 입력·기대값을 유지한 신규 727개, 누적 145명 조건 5,055개가 통과했다. 테스트 1,676개와 전체 26개 검사 묶음도 같은 최종 소스에서 두 번 통과했다. [보완 작업로그](WEB_MVP_WORKLOG_2026-09-16_PERSONA_ROUND8_FIXES.md). 아래 내용과 37개 실패 로그는 수정 전 진단 기록이며 그대로 보존한다. 실제 모델 평가·배포는 하지 않았다.

## 결론

**한국어 10명·영어 10명, 20~49세의 가상 설정 20명**을 추가했다. 기존 125명과 ID가 겹치지 않아 누적 145명이다. 실제 참여자는 0명이며 가상 인구를 대표 표본처럼 해석하면 안 된다.

신규 검사 **727개 중 690개 통과, 37개 실패**가 동일 소스·동일 기대값으로 두 번 재현됐다. 실패를 의미별로 묶으면 **8개 보완 유형**이다. 기존에 명시한 일간 배치 한계도 포함하므로 모두 처음 발견한 결함이라는 뜻은 아니다. 37개는 중복·후속 단언을 포함하며 독립 결함 수나 실제 사용자 실패율이 아니다.

이번에는 진단 데이터·도구·로컬 보고서만 추가했다. 제품 코드 수정, 배포, 운영 DB 변경, 유료 API 호출, 커밋·푸시, 노션 등록은 하지 않았다. **추가 모델 API 비용 $0.**

## 검증 방식

- 프로필별 작성 여정 83개 발언, 별도 상태 경계 37개, 실제 에이전트 코드에 모의 응답을 넣은 수집 경로 7개, 시간 예산 계산 11개, 초안 한도 검사 12개.
- 다수의 초기 여정은 공통 4턴 골격을 사용했다. 83개를 실제 모델이 생성한 서로 독립적인 대화로 해석하지 않는다. 휴식·삭제·복원 등 일부는 5~6턴으로 확장했다.
- 입력·모델 도구 인자 후보·기대값은 사람이 작성하는 방식으로 미리 정의했다. 실제 모델의 추출 정확도나 문장 자연스러움을 측정하지 않았다.
- 올바른 추출, 잘못된 모델 후보를 차단하는 검사, 정상 대조, 상태 저장·재로딩을 구분했다.
- 모의 공급자 콜백 17회, 모의 응답 반환 10회, 수집 결과를 읽고 의도적으로 종료한 경로 7개. 외부 공급자 호출은 0회다. 전체 답변 생성까지 끝낸 실제 사용자 대화는 아니다.
- 에이전트 수집 경로의 스키마·실행 오류는 0건이다. `captureResult.ok`와 실제 저장 내용을 검사하여 도구 실행 성공과 후보 정보의 채택을 혼동하지 않도록 했다.
- 초안 검사는 유효한 작성 카드에 대한 `goalFeasibilityIssue` 검사다. 다른 최종 승인 보호가 별도로 존재하므로 이 검사 통과만으로 운영에서 초안이 실제 확정됐다고 주장하지 않는다.

## 코드 근거와 반복되는 원인

1. [goalEvidenceScope.ts](../logs/sites/onju-web-mvp/supabase/functions/onju-agent-v2/goalEvidenceScope.ts)의 조건·현재 수준 검증은 일부 조건문과 미래 완료 표현을 다룬다. 그러나 미래 시점이 붙은 가용 시간, ‘목표’라는 명사로 표현한 결과를 현재 기준과 구분하는 범위는 부족하다.
2. 같은 파일의 역할 목록에는 `배우자`, `employer`가 없고 가정·미정의 모든 문법을 포괄하지 못한다. 예외 단어를 늘릴 때마다 다른 표현이 남는 구조적 한계다.
3. [goalCapacity.ts](../logs/sites/onju-web-mvp/supabase/functions/onju-agent-v2/goalCapacity.ts)는 알려진 수량 문법과 단일 범위 계산에 의존한다. 한 시간 반의 남은 `반`, 서로 다른 두 범위의 시간, quarter-hour를 각각 적절히 해석하지 못했다.
4. [goalFeasibility.ts](../logs/sites/onju-web-mvp/supabase/functions/onju-agent-v2/goalFeasibility.ts)의 확인 한도는 주간 시간·주간 횟수·회당 시간이다. 일간 예산 집합은 별도로 보존·검증하지 않는다.

따라서 다음 수정은 **저장 전 주체·시점·현재/목표·확정 여부 검증 → 하루/주간/회당 한도 보존 → 자연어 시간 표현 확대** 순서가 적절하다. 문구별 예외 추가뿐 아니라 같은 판단을 수집 필터와 최종 저장 양쪽에서 공유하고 정상 대조를 함께 검사해야 한다. 이번 요청에서는 수정하지 않았다.

## 검사 기대값 정정 이력

[최초 결과](../logs/persona-pilot-round8/2026-09-16T05-44-04-592Z/results.json)는 687/727 통과, 40개 실패였다. 제품은 바꾸지 않고 다음 두 사례의 3개 단언만 바로잡았다.

- KR-73: 직접 저장 함수는 부적절한 후보를 포함하면 전체 변경을 거절한다. 에이전트 수집 처리기는 먼저 부적절한 시간 후보를 걸러내고 사용자가 요청한 12주 변경을 저장한다. 둘은 다른 계층의 정상 계약이다. 에이전트 경로에서 처리 성공·12주 저장을 기대하도록 정정하고 **기존 가용 시간 보존 검사는 유지**했다.
- US-69: 복원된 분야의 과거 목표 근거는 예외를 던지지 않고 무시한다. 처리 성공 여부만 정정했고 **옛 목표가 되살아나지 않음·현재 수준 재확인 검사는 유지**했다.

최초 로그를 덮어쓰지 않았다. 나머지 제품 실패 37개를 통과로 바꾸거나 기준을 낮추지 않았다. 정정 이유는 결과 JSON의 `fixtureCorrections`에도 포함했다.
