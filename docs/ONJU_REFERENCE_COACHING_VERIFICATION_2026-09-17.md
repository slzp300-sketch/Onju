# 원문 기반 코칭 — 추가 검증과 완료 기준

## 판정 원칙

요청: 원문처럼 자연스럽게 사용자의 말을 이해하고 필요한 정보를 확인한 뒤 실행 가능한 계획을 제시하는 응대를 검증한다.

검사 개수를 실제 대화 품질 점수로 환산하지 않는다. 원문과 똑같은 문장 출력이나 모든 미래 대화의 100% 성공을 보장하지 않는다. 아래 네 층을 구분한다.

1. **코드·상태 검사:** 저장 근거, 최신 정정, 승인, 표시, 오류 처리의 명시한 조건.
2. **실제 모델 생성:** 현재 로컬 에이전트가 실제 제공자를 호출한 응답. 모의 응답은 제외.
3. **응답 내용 검수:** 질문의 유용성, 원문 수준의 설명과 개인화, 대화 연결을 직접 읽고 평가.
4. **사용자 확인:** 재현한 응답이 원하는 서비스 경험인지 최종 검수.

현재 실제 생성과 사용자 확인은 미실행이다. 무료 검사 통과를 이 단계의 완료로 대신하지 않는다.

## 이번에 재현하고 수정한 문제

| 문제 | 확인 방법 | 수정 |
| --- | --- | --- |
| 공통 지침과 도구 설명이 충돌 | 저장 도구와 명시적 캐시 지침에 과거의 질문 1개 강제·자동 초안 문구 잔존 | 공통 질문 정책을 재사용하고 상황별 응대·상세 요청 허용으로 통일 |
| 최신 질문 방식보다 과거 선호 우선 | 과거 하나씩 → 현재 묶어서 요청 검사 실패 | 최신 명시적 선호 우선. 관련 선호만 교체하고 다른 환경 선호 보존 |
| 변경 선호가 다음 턴에 사라짐 | 실제 respond 경로의 기억 필터 + 저장·재로딩·다음 턴 검사 실패 | 명시적 질문 방식 요청을 기억 필터에서도 인식 |
| 일반 텍스트 응답에서 질문 제한 우회 | 질문을 여러 문단에 분산하면 마지막 질문만 검사 | 질문이 담긴 모든 문단을 함께 검사 |
| 실제 평가 장치의 기준이 오래됨 | 평가 정책 상한이 여전히 질문 1개·글자 1,000으로 고정 | 현행 응답 계약의 최대치 재사용. 각 사례의 1개 질문 제한 등 더 엄격한 조건은 유지 |
| 재시도 비용 누락 가능성 | 응답·사용량을 잃은 요청 후 재시도 모의 검사 | 매 시도 전 예약. 비용 미확인 시 예약 유지, 알려진 비용과 불확실 상한을 구분 |

처음 네 실패를 먼저 재현한 뒤 수정했다. 실제 respond 필터의 후속 실패도 별도 재현 후 고쳤다. 기억 저장 시간은 인라인·일반 응답 모두 주입한 시각을 사용한다.

## 실제 평가 자료: 10개 흐름, 24개 사용자 발언

개인 원문을 복제하지 않고 일반화한 합성 자료이다. 실제 사람 10명이 테스트했다는 뜻이 아니다.

1. 운동 탐색·현재 동작 수준·목적 구분
2. 질문 하나씩 → 묶어서 → 하나씩 선호 정정
3. 모르는 수치·민감정보 거절·설명 우선
4. 운동 환경·피할 동작·실행량 제약
5. 충분한 정보 → 상세 초안 → 승인 아닌 설명 요청
6. 추천 기간과 사용자가 확정한 기간 분리
7. 유동 일정·정보 수집 중단·주제 전환
8. 실행 환경 정정과 나머지 조건 유지
9. 초안 → 명시적 승인 → 짧은 실행 보고 → 조정
10. 영어권 학습·유동 시간·목적 정정

자료: `logs/sites/onju-web-mvp/web-mvp/evals/onju-reference-coaching.json`

실제 평가는 로컬 최신 `runAgentTurn`과 기존 제공자 어댑터를 그대로 사용한다. 운영 배포나 사용자 데이터베이스 쓰기 없이 실행할 수 있다. 기존 사례 파일은 교체하지 않았다. 영어 사례는 언어·시차·국가·통화 정보를 실제 지역 설정 형식으로 전달한다.

## 내용 검수표

각 턴마다 아래 6항목을 0(실패)·1(미흡)·2(충족)로 기록한다. 이 작업의 엄격 완료 판정은 모든 항목 2점, 중대 실패 0건을 요구한다. 자동으로 2점을 채우지 않는다. 근거로 해당 응답의 실제 구절을 남긴다.

- `intent`: 현재 요청에 먼저 답했는가?
- `grounding`: 사실·추천·미정·정정을 구분했는가?
- `questionFit`: 이미 말한 것을 다시 묻지 않고 실제 판단에 필요한 질문만 했는가?
- `actionability`: 현재 단계에서 적절한 수준의 설명·실행 방법을 제시했는가? 정보 부족 단계에서 계획 강요를 하지 않았는가?
- `readability`: 문단·강조·목록이 유용하고 핵심이 명확한가?
- `continuity`: 환경·선호·실행 보고·승인 상태를 후속 대화에서 유지하는가?

중대 실패: 근거 없는 기간·실행량·건강 수치 확정, 승인 없는 계획 활성화, 거절한 정보 재요구, 가짜 저장·알림 약속, 입력한 정보를 반복 수집, 요청과 무관한 고정 대본 응대 등.

검수 파일의 구조 검사는 인간의 의미 판단을 대체하지 않는다. 실제 답변에 존재하는 인용을 요구하지만, 인용 자체가 적절한 점수를 증명하지는 않는다. 검수자가 내용을 읽고 평가해야 한다.

## 완료로 오인하지 못하게 하는 장치

`reference-coaching-evaluation.mjs`는 실제 제공자 정보·사용량·전체 사례와 턴·실패 기록·소스 해시·자료 해시·검수 대상 응답 해시를 확인한다.

- 실제 보고서 없음 → `not_run`
- 일부 사례 누락, 오래된 소스, 빈 응답, 실패한 턴 → `failed`
- 자동 검사만 통과 → `awaiting_review`
- AI의 내용 검수만 있거나 사용자 확인 없음 → `awaiting_user_acceptance`
- 현재 자료 전체와 해당 소스의 응답을 검수하고 사용자가 확인 → `validated_scope`

마지막 상태도 **명시한 사례·소스·검수한 응답에만 유효**하다. 미지의 사용자 발언이나 다음 확률적 생성 결과까지 보장하지 않는다. 실제 보고서는 실행 ID별로 보존하여 latest 파일 갱신으로 이전 근거를 잃지 않도록 했다.

## 비용과 실행 순서

이번 변경에는 추가 모델 API 호출이 없다. Codex 자체 사용량과는 별개다. 유료 실행에는 기존의 명시적 실행 옵션과 비용 한도가 필요하며, 오프라인 모드에서는 실행을 막는다. 무료 계획 출력은 키 파일을 읽지 않는다.

1. 무료 전체 검사와 준비 상태 확인.
2. 사용자가 승인한 소규모 예산 범위에서 대표 사례부터 실제 실행. 요청한 **$1은 전체 24턴 완료 견적이 아니라 최초 소규모 평가 상한 제안**이다.
3. 실제 응답·호출 수·측정 비용을 확인하고 실패를 수정. 이후 필요한 범위와 추가 예산을 판단한다. 원가표는 실제 유료 실행 전에 최신 단가와 대조한다.
4. 전체 사례의 응답을 내용 검수하고 사용자에게 제시. 부분 실행만으로 전체 완료를 선언하지 않는다.
5. 사용자 확인 후 배포 여부를 별도로 결정한다.

비용 예약은 확인된 단가로 계산한 보수적 추정이다. 제공자 청구 자체를 강제 제한하는 기능은 아니다. 사용량을 잃은 요청은 비용 0으로 표시하지 않고 불확실 상한으로 별도 기록한다.

무료 확인 명령:

```powershell
node web-mvp/scripts/verify-offline.mjs
node web-mvp/scripts/report-reference-coaching.mjs
node logs/sites/onju-web-mvp/web-mvp/scripts/run-gemini-candidate-eval.mjs --dry-run --reference-coaching --all --provider openai
```

보고서·검수 파일이 준비되면 읽기 전용으로 `report-reference-coaching.mjs --report <보고서.json> --review <검수.json>`을 실행한다. 유료 실행 승인 전에는 dry-run만 사용한다.
