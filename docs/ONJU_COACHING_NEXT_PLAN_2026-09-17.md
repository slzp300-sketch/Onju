# 온주 대화 품질 고도화 — 배포 이후 실행 계획과 결정 사항

작성: 2026-09-17(KST). 사용자 요청: 현재까지의 작업을 먼저 배포하고, 제공한 운동 관리 대화 수준에 도달하기 위한 방안·계획·사용자 결정 사항을 정리한다.

## 1. 결론

목표는 **정해진 설문을 완료시키는 챗봇이 아니라, 사용자가 말한 내용으로 판단하고 계획과 실행을 함께 다듬는 코치**다.

핵심은 질문을 없애거나 답변을 무조건 길게 만드는 것이 아니다. **정보가 부족하면 확정은 보류하되, 이해·설명·도움까지 멈추지 않아야 한다.** 대화 판단과 실제 계획 저장·활성화의 조건을 분리한다.

이번에는 기존 개발 내용을 배포했다. 아래 신규 고도화 계획은 검토안이며, 전부 구현되거나 원문 수준으로 검증됐다는 뜻이 아니다. 원문의 문장이나 모든 미래 응답의 품질을 100% 보장할 수 없다. 합의한 실제 사례에서 요구한 기능과 품질을 충족하는 것을 완료 기준으로 삼는다.

## 2. 확인된 사실과 아직 모르는 것

### 실제로 확인한 것

- 배포 전 기본·시험용 에이전트에 원문 사용자 발언 3개씩, 총 6턴을 그대로 입력했다. 원문 ChatGPT 답변은 모델에 주입하지 않았다.
- 두 버전 모두 기간 확인에 머물렀다. 세 번째 답변은 각각 107자·213자였으며 원문 2,489자와 비교해 현재 수준의 해석·실행 방법·기록과 조정 설명이 부족했다. **길이 자체가 실패 기준은 아니다.**
- 사용자가 기간에 답하지 않았으므로 기간 확인 자체는 타당했다. 문제는 설계와 관리를 요청하고 상세한 현재 상태를 제공했는데도 유용한 설명 없이 같은 관문에 머문 것이다.
- 이 시험은 당시 배포본에 대한 결과다. 이번에 새로 배포한 소스의 실제 응답 품질을 대신 증명하지 않는다.
- 현재 소스는 고정 질문으로 답변을 덮어쓰던 경로 제거, 관련 질문 최대 3개 허용, 상세 출력·맥락 기억·최신 선호 정정 등을 이미 반영했다. 새로 전부 만들기보다 실제 배포본에 남은 실패부터 확인해야 한다.
- 현재 `requestedDetailedReply`는 주로 ‘자세히/상세히/구체적으로’ 같은 표현에 반응한다. ‘설계해주고 같이 관리해줘’만으로 상세 출력 분기가 선택된다고 보장할 수 없다. 이는 **코드에서 확인한 개선 후보**이며, 새 배포본의 실제 품질 실패로 단정하지 않는다.

### 이번 배포에서 확인한 것

- 기존 공개 주소와 공개 범위 유지: https://onju-web-mvp.slzp300.chatgpt.site
- 화면과 서버 15개, DB 전진 변경 4개 적용. 기존 앱 전용 알림·일정 해석 함수는 변경하지 않았다.
- 기존 대화 163개 보존. 소유 정보 없는 137개는 임의로 소유권을 부여하지 않는다. 사용자 승인에 따라 새 대화 시작을 안내한다.
- 기본·시험용 경로의 빈 테스트 세션에서 생성/조회, 잘못된 토큰 차단, 내보내기, 삭제 재시도, 삭제 후 재접근 차단을 확인했다.
- 자동 검사 2,231개 통과 근거를 보유한다. 이는 프로그램의 계약과 회귀 검사이지 실제 자연어 품질 인증이 아니다.
- 이번 배포·접근 점검의 모델 API 호출은 0회다. 직전 원문 비교 시험의 서버 추정 비용은 합계 **$0.180190**이며 제공자 청구서 대사 금액은 아니다. Codex 사용료·기존 호스팅/DB 비용과 별개다.

## 3. 원문에서 가져올 경험

| 가져올 것 | 온주 적용 방식 | 그대로 복제하지 않을 것 |
| --- | --- | --- |
| 목표의 의미 해석 | 원하는 결과와 현재 상태가 제안에 어떤 영향을 주는지 설명 | 유명인과 같은 체형이나 성과 보장 |
| 필요한 정보 요청 | 이미 아는 것은 건너뛰고, 계획을 바꾸는 정보만 확인 | 모든 사용자에게 똑같은 9문항 설문 |
| 구체적인 실행 방법 | 행동, 실행량, 순서, 완료 기준, 쉬거나 줄이는 조건 제시 | 미확정 기간·주당 횟수·장비를 사실로 저장 |
| 왜 그렇게 하는지 설명 | 핵심 선택의 이유를 사용자의 말과 연결 | 근거 없이 정확해 보이는 수치 제시 |
| 함께 관리하는 방법 | 짧은 실행 기록 → 해석 → 다음 실행 조정 | 지원하지 않는 선제 메시지·자동 연락 약속 |
| 읽기 좋은 답변 | 핵심 요약, 필요한 소제목·굵게·목록, 충분한 설명 | 매 답변에 동일한 목차를 강제하거나 불필요하게 장문 출력 |

운동 사례의 건강·영양 수치를 일반 규칙으로 채택하지 않는다. 장비, 피해야 할 움직임 등 실행 가능성과 안전에 필요한 조건은 확인한다. 민감정보는 최소한으로 요청하고 거절을 존중한다.

## 4. 제안하는 동작 구조

```text
사용자 발언 + 최근 대화 + 확인된 기억
                    ↓
한 에이전트가 현재 의도와 필요한 도움을 판단
       ├─ 설명·제안·필요한 질문 → 자유로운 대화
       └─ 저장·수정·확정 요청 → 근거·권한·승인 검사 → 실제 반영
                    ↓
핵심 행동을 간단히 표시 + 필요할 때 상세 설명
                    ↓
실행 기록을 받으면 다음 실행을 조정
```

### 각 부분의 역할

- **규칙:** 근거 있는 사실만 저장, 이미 아는 정보 재질문 금지, 모름·거절·유동 존중, 승인 없는 확정 금지, 답변의 가독성·안전·권한 경계. 질문 순서를 강제하는 대본은 두지 않는다.
- **기억:** 사용자 발언으로 확인한 사실, 아직 모르는 정보, 거절한 정보, 추천했지만 동의받지 않은 정보, 최신 정정을 구분한다. 실제 제공된 근거와 시점을 보존한다.
- **지식:** 분야별로 계획을 만들 때 필요한 판단 기준과 좋은 설명 예시. 개인 원문을 모든 사용자에게 보내는 공통 프롬프트나 고정 답변으로 넣지 않는다.
- **도구:** 계획 저장·승인·변경, 실행 기록, 회고, 데이터 관리. 정상 대화 문장을 사후에 정해진 문구로 치환하는 용도로 사용하지 않는다.
- **평가:** 실제 응답을 사용자의 요청·상태·이전 대화와 함께 읽는다. 모의 응답, 글자 수, 특정 키워드 포함 여부만으로 합격시키지 않는다.

처음부터 여러 AI가 매 턴 서로 평가하는 구조는 권하지 않는다. 현재 단일 에이전트와 기존 모델 구성을 먼저 검증하고, 필요한 경우에만 별도 평가 환경에서 비교한다. 모델 교체·자체 모델·파인튜닝은 이번 구조 개선의 필수 전제가 아니다.

## 5. 단계별 실행 계획

각 단계에서 **① 요구 충족 검토 → ② 회귀·부작용 검토**를 진행하고 근거를 남긴다. 이미 통과한 동작을 이유 없이 다시 개발하거나 모든 테스트를 반복하지 않는다.

| 단계 | 할 일 | 완료 조건 | 비용·진행 조건 |
| --- | --- | --- | --- |
| 1. 새 배포본 기준선 | 원문 3개 발언을 새 세션에 동일하게 입력. 실제 모델·호출 수·답변·비용·배포 소스 연결 기록 | 어느 턴에서 어떤 설명이 부족한지 실제 응답 근거로 식별. 기존 배포본 결과와 분리 | 유료 평가 예산 승인 후 작은 1회 실행. 실패 응답을 좋은 결과가 나올 때까지 재생성하지 않음 |
| 2. 대화 판단과 확정 조건 분리 | 기간/현재 위치/여건 확인은 유지하되 정보 수집 중에도 접근 방향·추천 이유·관리 방식을 설명. 누락 목록이 질문 순서를 결정하지 않게 점검 | 기간 미정에서도 요청에 답하고, 미정 값은 확정 사실로 저장되지 않음. 답한 정보·거절한 정보를 재수집하지 않음 | 우선 무료 코드·계약 검사. 1단계에서 이미 충족하면 중복 수정 생략 |
| 3. 요청에 맞는 설명 깊이 | ‘설계해줘/같이 관리해줘’처럼 의도를 전달한 말도 충분한 설명 요청으로 판단. 짧은 답변 선호는 존중 | 명시적 ‘자세히’라는 단어 없이도 필요한 이유·방법·기록 안내가 나옴. 단순 확인은 짧게 유지 | 답변 길이만 늘리지 않음. 출력량 증가에 따른 비용은 실제 측정 |
| 4. 실행과 관리 연결 | 충분한 정보가 모이면 실제 여건에 맞는 주간·일일 실행안, 완료 기준, 축소 대안, 짧은 기록 예시와 다음 조정 기준 제시 | 계획 카드의 첫 화면은 목표+행동이 명확. 상세 대화와 저장 계획이 모순되지 않음. 실행 보고 후 설문을 다시 시작하지 않음 | 기존 계획·일일 점검 기능을 연결해 검증. 불필요한 새 엔진 개발 금지 |
| 5. 일반화·사용자 검수 | 원문 외 운동 변형·독서·학습·이직·영어·정정·거절·유동 일정 등 준비된 흐름 평가. 사례 일부는 구현 중 정답으로 보지 않는 보류 사례로 유지 | 아래 의미 기준 충족, 중대 실패 0건. 재현님이 실제 답변 비교를 보고 승인 | 1차 비용 결과를 보고 다음 묶음의 예산 승인. 전체 성공을 가상 사용자 수로 대신하지 않음 |

최초 평가에서 이미 개선된 부분은 완료 처리하고 남은 실패에만 집중한다. 남은 작업량과 전체 비용은 새 배포본의 실제 응답을 본 후 좁혀 산정한다. 현재 정보로 고정된 완료 날짜나 총액을 보장하지 않는다.

## 6. 원문 입력에 기대하는 응대

아래는 출력 대본이 아니라 **수행해야 하는 역할**이다. 문장·질문 순서가 달라도 목적을 충족하면 된다.
발언 예시는 원문과 같은 유형으로 새로 쓴 합성 문장이다(원문은 저장소에 두지 않는다).

### 첫 발언: 운동을 습관으로 만들어서 체력을 키우고 싶어

- 막연한 목표를 어떤 변화로 구체화할지 이해하기 쉽게 안내한다.
- 답변을 기간 질문 하나로만 끝내지 않는다. 사용자에게 유용한 방향 설명과 관련 질문을 제공한다.
- 한 발언만으로 확정된 주간 운동표를 생성하지 않는다.

### 두 번째: 계획을 짜 주고 꾸준히 같이 챙겨 줘

- 어떤 방식으로 설계하고 관리할지 설명한다. 사용자가 해야 하는 입력 부담도 알려준다.
- 현재 수준, 실행 가능한 여건, 희망 기간처럼 현재 결정에 필요한 정보를 자연스럽게 요청한다. 이미 받은 정보는 생략한다.
- 완료/실행량/어려움 같은 짧은 기록으로 이어갈 수 있음을 안내한다. 실제 지원하지 않는 자동 연락은 약속하지 않는다.

### 세 번째: 현재 상태·운동 기록·홈트 선호·원하는 체형 제공

- 현재 수행 기록과 지구력의 어려움, 집에서 하고 싶은 선호를 각각 제안에 반영한다.
- 무엇을 보완하고 어떤 방식으로 접근할지, 알려준 사실에 근거해 설명한다.
- 기간과 가능한 횟수·시간·장비가 미정이면 필요한 것을 확인한다. 대신 **왜 필요한지와 이미 정할 수 있는 방향·관리 방법**도 제공한다.
- 기간·장비가 확인되지 않았다는 이유로 요약 한 줄과 똑같은 기간 질문만 내놓지 않는다.
- 원문의 ‘9는 모르겠어’는 원문 AI가 질문 9번을 했기 때문에 성립한다. 온주가 질문 9번을 하지 않은 정확 재생 시험에서는 그 표현의 지시 대상이 불분명함을 결과 해석에 기록한다. 이 한 문구만으로 기억 실패 판정을 하지 않는다.

### 필요한 여건이 확인된 다음

- 첫 주에 실제로 무엇을 얼마나 할지, 완료 기준과 조정 방법이 있는 실행안을 제시한다.
- 초안의 구체성과 실제 조건의 일치를 검사한다. 설명 요청을 승인으로 오인하지 않는다.

## 7. 품질 합격 기준

기존 검수표의 6항목을 유지한다: **의도 반영, 사실 근거, 질문 적합성, 실행 가능성, 가독성, 대화 연속성**. 각 항목을 실제 답변의 근거 구절과 함께 0~2점으로 검토한다.

- 현재 요청에 먼저 답하고 다음 질문이 그 답에 연결되는가?
- 사용자가 알려준 정보를 요약만 하지 않고 판단에 활용하는가?
- 기간 미정과 기간 거절, 모름과 0, 추천과 확정을 구분하는가?
- 실행안이 필요한 단계에서는 무엇을 언제/어떤 조건에서 어떻게 할지 명확한가?
- 자세한 설명을 읽은 뒤에도 지금 할 행동을 쉽게 찾을 수 있는가?
- 정정·쉬는 날·실행 보고·재접속 후에도 이전 맥락과 승인 상태를 유지하는가?

해당 사례에서 6항목 모두 충족하고 중대 실패가 없어야 그 사례를 완료로 표시한다. 이미 답한 정보의 반복 수집, 사실 날조, 승인 없는 활성화, 불가능한 기능 약속은 평균점수로 상쇄하지 않는다.

자동 검사는 저장·권한·출력 계약을 담당하고, 의미 품질은 실제 응답 검수와 사용자 최종 확인을 거친다. 이는 OpenAI 공식 [평가 지침](https://developers.openai.com/api/docs/guides/evaluation-best-practices)의 작업별 평가와 인간 판단 결합 원칙을 참고한 것이다. 기존 로컬 평가 도구를 사용하며 새 외부 평가 플랫폼 도입을 요구하지 않는다.

## 8. 재현님이 확정한 사항 (2026-09-17, 아래 추천안을 대체)

1. 실행 방법, 선택 이유, 관리 방식을 충분히 설명한다. 단순 확인까지 길게 늘리지는 않는다.
2. 필요한 정보가 부족하면 **초안을 먼저 만들지 않는다**. 임시·조건부 예시로 실행안을 우회 생성하지 않는다. 대신 원하면 어떤 도움을 받을 수 있는지와 좋은 접근 방향을 제안한다.
3. 현재 판단에 필요한 미확인 정보는 **한 번에** 묻는다. 이미 받은 정보·거절·모름은 반복 수집하지 않는다. 이전의 '최대 2~3개' 추천은 철회한다.
4. 최초 실제 평가 **$1** 승인. 추가 평가 승인으로 확대 해석하지 않는다.

이 결정은 문서 앞부분의 검토안 중 조건부 실행 예시 허용·질문 개수 제한보다 우선한다. 실제 평가는 원문 재생 3턴과 별도로 표시한 정보 보충 1턴을 사용한다. 정보가 부족한 원문 세 번째 턴에서 실행표가 나오지 않는 것은 이번 기준상 올바른 행동이다.
