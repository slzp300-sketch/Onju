## 저장 동작의 범위

- 미전송 작업에는 작성한 계정의 사용자 ID를 기록하고 그 계정의 세션 토큰으로만 전송한다. 다른 계정의 보관 작업은 현재 계정 대기 개수에 포함하지 않는다.
- 로그아웃하면 표시 데이터와 조회 캐시는 지워지지만 미전송 변경은 기기에 남는다. 해당 계정으로 재로그인하면 전송한다. 기기 저장 공간 부족은 보관 성공으로 표시하지 않고 안내한다.
- 데이터베이스 오류가 계속되는 선두 작업은 FIFO를 지키기 위해 뒤 작업의 전송을 보류할 수 있다. 자동 폐기 대신 오류 원인을 해결하고 재시도한다.
- 이 변경은 로컬 저장을 보강한다. 앱 제거·브라우저 데이터 삭제·기기 고장까지 복구하는 서버 백업 기능은 아니다.
- 오프라인에서 새 계정으로 인증하는 기능을 구현한 것은 아니다. 이미 복원 가능한 세션과 그 계정의 확인된 캐시만 사용한다.
- Web Locks를 지원하는 환경에서는 같은 출처의 탭 사이에서도 인증 변경을 직렬화한다. 지원하지 않는 WebView의 대체 경로는 같은 앱 인스턴스 안에서 직렬화하며, 작업 소유자·전송 토큰·응답 세대 검사는 별도로 유지한다.

## 운영·실기기에서 남은 확인

1. **메일 Redirect URL 허용 목록**: `docs/NATIVE_OAUTH.md`의 웹 `/reset-password` 및 `onju://reset-password`를 실제 Supabase 설정과 대조해야 한다. 이번 작업에서 콘솔 설정을 바꾸지 않았다.
2. 실제 SMTP로 메일 도착·만료·재발급·동일 브라우저/앱의 PKCE 복귀를 확인해야 한다. 다른 기기·시크릿 창에는 원래 검증 값이 없을 수 있다.
3. Android에서 앱 실행 중·종료 후 복구 링크와 카카오 콜백, 구글·카카오 취소·거절을 확인해야 한다. 이번 검사는 SDK 모형과 브라우저로 수행했다.
4. 실제 두 테스트 계정으로 로그아웃·재로그인·오프라인 편집·재연결과 사진 포함 탈퇴를 확인해야 한다. 이번에 실제 계정 비밀번호를 바꾸거나 사용자 데이터를 삭제하지 않았다.
5. 알림·홈 위젯·권한·실기기 화면 검증과 새 커뮤니티 SQL의 적용·운영 확인이 남아 있다. 기능 보완·검증 이후에 서명 빌드와 배포를 진행한다. 이번 회차에서 Android 동기화·서명 AAB·스토어 제출은 하지 않았다.

Supabase의 [재설정 API](https://supabase.com/docs/reference/javascript/auth-resetpasswordforemail), [비밀번호 인증](https://supabase.com/docs/guides/auth/passwords), [네이티브 딥링크](https://supabase.com/docs/guides/auth/native-mobile-deep-linking)를 확인했다. 코드 교환 이벤트 순서는 설치된 `@supabase/auth-js` 구현과도 대조했다. 검사 통과를 실제 메일·기기 인증 또는 출시 완료의 증거로 사용하지 않는다.

노트9에는 예시 데이터용 `com.onju.app.uiverify`와 별도로 **온주 서버 검증**(`com.onju.app`)을 새로 설치했다. 기존 패키지가 없음을 두 차례 확인한 후 교체 옵션 없이 설치했다. 자동 승인 검토가 먼저 `install -r` 명령을 기존 운영 앱 교체 위험으로 거절했고, 해당 명령은 실행되지 않았다. 이후 기존 앱이 발견되면 중단하는 검사와 신규 설치 방식으로 위험을 제거했다. 기존 예시 앱·계정·기록은 삭제하지 않았다. 새 계정도 아직 만들지 않았다.

### 이어서 진행할 순서

1. 테스트 계정 2개를 준비한다. 새 비밀번호 입력과 약관 동의는 사용자가 앱에서 직접 진행한다. 비밀번호·세션 토큰은 채팅·소스·검사 로그에 남기지 않는다.
2. 계정 A 로그인 → 신규 검증용 할 일 1개 오프라인 보관 → 앱 재실행 후 유지 → 계정 B 로그인 후 A 기록 미노출·미전송 → A 복귀 후 원래 요청 확인을 검사한다. 기존 기록 편집·삭제는 하지 않는다.
3. 동기화 성공 검증은 현재 저장 규격이 적용된 승인된 검증 서버가 있어야 한다. 운영 SQL 적용이나 별도 서버 배포는 이번 작업의 보류 범위이므로 수행하지 않는다.
4. 서버 준비 이후 동일 요청의 서버 반영·중복 없음·재조회 결과를 확인하고 그때 전체 검증을 완료한다. 현재 보존 회귀 통과를 서버 준비 완료로 간주하지 않는다.
