# 온주 GPT‑4.1 / GPT‑4.1 mini 실제 비교

검증일: 2026-09-04, 한국시간 10:14~10:22 API 실행.

## 판단

현재 알파에서는 GPT‑4.1을 유지할 가치가 있다. 특히 목표를 **제안만 하는 것과 사용자가 확정한 것을 구분**하는 능력이 이번 표본에서 더 나았다. 다만 전면적인 성능 해결책은 아니며, 다음 우선순위는 모델 추가 상향이 아니라 승인·저장·단계 전환의 서버 검증이다.

간단한 일정 추출·수정은 mini도 수행했다. 향후 비용을 줄일 때 단순 일정 처리와 목표 설계를 나눠 쓰는 방식을 검토할 수 있지만, 이번에 혼합 라우팅을 구현하거나 검증하지는 않았다. 운영 함수와 모델 설정, 실제 사용자 세션은 변경하지 않았다.

## 어떻게 비교했나

- 모델: `gpt-4.1-2025-04-14`, `gpt-4.1-mini-2025-04-14`. 응답 메타데이터에서도 동일 스냅샷 확인.
- 일반 사례 8개와 구조 한계 확인 사례 1개 × 2회 반복 × 2모델 = **36개 사용자 턴 응답**, 내부 Responses API 호출 **80회**.
- 사용자의 기존 문제와 유사한 합성 사례를 사용했다. 같은 초기 상태·대화 이력·사용자 메시지를 두 모델에 전달했다. 두 번째 반복에서는 모델 실행 순서를 바꿨다.
- 운영 소스의 프롬프트, 스키마, 저장 검증, 도구 반복 루프를 복제·고정했다. 원본 네 파일의 SHA-256과 사례 해시를 원시 결과에 기록했다. 비교 중 프롬프트를 수정하지 않았다.
- 모델만 비교하기 위해 이전 답변에서 분기되는 전체 신규 대화 대신, **동일한 이력이 주어진 한 턴의 판단**을 비교했다. 따라서 사용자가 계획 완성까지 몇 턴 입력해야 하는지는 측정하지 않았다.
- 기존 DB 저장 대신 요청/응답 안의 테스트 상태를 사용했다. 운영 DB나 사용자 기록에 쓰지 않았다. 여기서 “저장”은 운영과 같은 검증 로직을 거친 반환 상태를 의미한다. DB 영속 저장 성공률은 별도 평가 대상이다.
- 한국시간 프롬프트 시각을 고정했고 OpenAI `store:false`를 사용했다. 앱과 다른 부분은 원시 결과의 manifest에 명시했다.
- 임시 평가 함수는 난수 토큰으로 보호하고 2시간 만료를 걸었다. 토큰 없는 요청은 403이었다. 종료 후 원격 함수, 생성된 로컬 함수 복사본, 로컬 임시 토큰을 삭제했다. 테스트 함수는 재현 스크립트로 다시 생성할 수 있다.
- 429에만 재시도하도록 계측했으나 이번에는 **429 및 요청 실패 모두 0회**였다. 실행 간 간격은 응답 시간에서 제외했다.

자동 상태 검사에 답변 원문 검토를 더했다. 문단·물음표 개수만으로 실제 대화 품질을 판단하지 않았다. 외부 사람의 맹검 평가는 아니며, 일부 사례는 현 프롬프트 예시와 비슷한 회귀 사례다. 일반화된 모델 정확도나 실제 고객 만족도를 입증하는 결과는 아니다. 이런 작업별 평가와 정성적 검토의 병행은 [공식 평가 가이드](https://developers.openai.com/api/docs/guides/evaluation-best-practices)를 참고했다.

## 원문에서 확인한 차이

### 미정 정보를 다시 묻는 문제

입력: “평일은 6시 기상 23시 취침. 주말 기상 취침은 전혀 일정하지 않아, 그때그때 알려줄게”

mini 1회차는 주말을 미정으로 남겨두면서 “주말 중 가장 최근 알려줄 취침 시간이 언제였나요?”라고 질문했다. 4.1은 두 번 모두 평일 반복 일정으로 이어갔다. mini 2회차는 개선된 응답을 보여, 한 번의 답변만으로 모든 동작을 단정할 수 없다.

### 승인하지 않은 초안이 실제 확정 상태에 들어가는 문제

입력: “아니, 그건 부담돼. 더 가벼운 다른 초안을 제안해줘. 아직 확정하지는 말고.”

mini 두 번 모두 답변은 “초안”이라고 했지만 반환된 `goal_card`에 `durationWeeks:2`와 `weeklyActions: 주2회·5분`을 저장했다. 4.1은 새 초안을 제안하되 기간 0, 행동 빈 배열을 유지했다. 이는 말투보다 중요한 상태 변경 차이다.

### GPT‑4.1도 놓친 부분

기상만 알려진 일요일의 취침 시간이 아직 남아 있는데, 토요일 취침 답변 뒤 바로 반복 일정 질문으로 이동했다. 일요일 기상·취침을 부분 저장하려다가 검증에 실패했는데도 “알려준 부분을 모두 반영했다”는 문장을 만들었다. mini 2회차도 “일요일 기상 7시는 저장했다”고 말했으나 시간 지도용 상태에는 일요일이 없었다. 이 사실은 대화 이력에는 남아 있어, 사실을 잊은 문제와 지도 반영 실패를 구별해야 한다.

금요일 23:00~토요일 01:00 사례에서 4.1은 금요일 구간 저장이 누락됐는데도 두 번 모두 완료했다고 답했다. mini는 두 번 모두 금요일 종료를 23:59로 바꿔 1분을 잃었다. 실패를 숨기는 설명과 시간 왜곡은 둘 다 수정 대상이다.

## 비용 해석

계산 단가는 100만 토큰당 입력/캐시 입력/출력 순서로 4.1 **$2 / $0.50 / $8**, mini **$0.40 / $0.10 / $1.60**이다. [GPT‑4.1 공식 요금](https://developers.openai.com/api/docs/models/gpt-4.1), [GPT‑4.1 mini 공식 요금](https://developers.openai.com/api/docs/models/gpt-4.1-mini).

계산식: `(입력−캐시입력)×입력단가 + 캐시입력×캐시단가 + 출력×출력단가`, 전체를 1,000,000으로 나눈다. 한 사용자 응답에 필요한 모든 내부 호출을 합산했다.

- 4.1: 입력 141,185, 그중 캐시 57,984, 출력 5,113 → **$0.236298**.
- mini: 입력 127,287, 그중 캐시 32,128, 출력 4,826 → **$0.048998**.
- 전체 검증의 모델 사용량 기반 비용: **$0.285296**. 청구서를 대조한 결제액은 아니며, 세금·환율·Supabase 비용은 제외한다.
- 응답당 관측 비용 비율은 **4.82배**다. 할인 없이 같은 토큰량을 계산하면 **5.51배**다. 모델 단가 5배와 실사용 비율이 다른 이유는 도구 호출 수·생성 길이·캐시 적중량이 다르기 때문이다.
- 이 테스트와 같은 평균 분량을 1,000번 처리하면 약 **$13.13 대 $2.72**다. 캐시 할인 없이 계산하면 약 **$17.96 대 $3.26**다. 길어진 사용자 이력이나 다른 사례 비중에는 그대로 적용할 수 없다.
- 고정된 시각과 반복 사례는 캐시가 잘 맞는 환경이다. 실제 앱은 시각과 이력이 변하므로 관측 비용만으로 월간 예산을 확정하지 않는다.

## 다음 수정 우선순위 — 이번에는 구현하지 않음

1. **초안과 확정 상태 분리**: draft를 별도로 저장하고, 승인할 draft ID/버전에 대해 서버가 확인한 경우에만 확정 상태를 변경한다. 현재는 `respond.goal_card`도 곧바로 확정 값을 덮어쓸 수 있다. `evidence_verified:false` 역시 로그만 남기고 저장을 막지 않는다. 문자열 일치만으로 승인을 판정하는 방식으로 되돌리는 것이 해법은 아니다.
2. **기상·취침의 부분 정보 보존과 전환 조건**: 요일별 기상/취침을 각각 미정으로 표현한다. 모르는 값을 미루는 것과 아직 답할 수 있는 질문을 건너뛰는 것을 구별한다.
3. **저장 결과를 답변과 맞추기**: 도구 결과를 부분 성공/항목별 거절로 반환하고, 저장된 상태에 없는 항목을 완료했다고 말하지 못하도록 검사한다.
4. **자정 경계 지원**: 종료 24:00 또는 다음 날 경계를 올바르게 표현한다. 현재 시간 검증과 `start<end`만으로는 원래 구간을 보존하지 못한다.
5. **대화·UI는 별도 검증**: 중복 질문·불필요한 요약을 줄이고, 실제 모바일 화면에서 줄바꿈·가독성·자동 스크롤을 검증한다. 모델 변경은 스크롤 구현을 바꾸지 않는다. 이번 API 비교는 화면 사용성 테스트를 대체하지 않는다.

위 개선 후에는 전체 다중 턴 대화, 더 긴 이력, 처음 보는 사용자 표현, 실제 사용자 평가를 포함해 다시 비교해야 한다. 제한된 표본으로 전면 모델 변경이나 과금 플랜을 확정하지 않는다.
