## 전체 피드백과 다음 우선순위

1. **기록·실행 흐름과 네 탭의 역할은 분명해졌다.** 종이·숲 테마도 일관적이다. 다만 홈의 나무·목표·달력이 상단을 많이 차지해 체크까지 스크롤이 필요하다. 다음 UX 작업은 상단 요약을 접는 방식과 오늘 기록 접근성을 우선 검토한다.
2. **알림 예약 실행부를 다음 기능 보완 우선순위로 둔다.** 이번에는 설정과 공통 spec 생성을 고쳤다. `useNotificationScheduler.ts`의 웹 폴백은 아직 공통 spec을 사용하지 않는다. 지난 시각 즉시 발송, 요일·자정 처리, 최신 완료 기록 반영을 점검해야 한다. 네이티브 예약의 계정 전환/취소 순서와 Web Push 동기화 실패·재시도도 무료 모의 검사 후 실기기로 확인한다.
3. **편집 화면 이탈 보호를 확장한다.** 일기의 앱 버튼·새로고침 보호는 구현했지만 Android 시스템 뒤로가기와 브라우저 뒤로가기 차단까지 보장하지 않는다. 습관·루틴·목표 폼에도 작성 중 이탈, 키보드와 저장 버튼, 긴 제목·큰 글꼴을 순차 확인한다.
4. **실서비스 검증은 출시 차단 항목으로 남는다.** 실제 비밀번호 재설정 메일·네이티브 복귀, 두 계정 오프라인 전환, 커뮤니티 SQL·운영 처리, 알림·위젯, SDK·서명·스토어 자료를 완료한 뒤 배포한다. 현재는 출시 준비 완료가 아니다.

다음 작업은 위 기능 보완과 실기기 검증을 이어간다. AI 개발과 유료 API 평가를 재개하지 않는다.

기능·실기기 검증 완료 후에만 SDK·서명·버전·스토어 자료와 내부 테스트 배포 준비로 넘어간다. 현재 계획 정리에서는 코드 추가 수정, 운영 DB 적용, 실제 메일 발송, 유료 테스트, 배포를 실행하지 않았다.


## 알림 안정화·입력 보호 후속 완료

사용자가 승인한 계획의 1·2단계를 구현했다. 운영 서비스와 AI 관련 코드는 이 회차에서 변경하지 않았다. 새 SQL과 알림 Edge Function은 로컬 소스만 수정했으며 운영에 적용하지 않았다.

### 알림 변경

- 웹 폴백도 `buildReminderSpecs`를 사용한다. 잘못된 시간, 빈 선택 요일, 비활성 신앙 루틴, 같은 항목의 중복 시간을 제외한다. 자정(00:00 포함)과 일요일 20시를 처리한다. 지난 시간은 앱 실행 시 따라 보내지 않고 절전 복귀 후 1분 이상 늦은 예약도 건너뛴다.
- 발송 기록은 계정·알림·예약 시각별로 구분한다. Web Locks 지원 브라우저에서는 여러 탭의 발송 검사·기록 및 구독 교체를 직렬화한다.
- Android 예약 취소→등록과 웹 구독→서버 저장을 순차 처리한다. 연속 변경은 최신 요청을 반영하고, 계정 전환 즉시 이전 요청을 무효화한다. 로그아웃은 Android 예약·알림함 또는 해당 브라우저 구독을 정리한다. 해제 실패도 안내 및 재시도 대상이다.
- 서버 요청은 시작 계정의 토큰에 고정한다. 진행 중 토큰 갱신도 최신 요청으로 이어간다. 웹 요청은 15초 제한, 실패 시 2초부터 최대 60초 간격 재시도, 온라인 복귀·앱 활성화·수동 재확인을 제공한다.
- 데이터 복원 전의 빈 기본값으로 서버 예약을 지우지 않는다. 알림 권한은 기기별이므로 권한 거절 시 해당 기기 구독만 해제하고 다른 기기의 계정 예약을 임의로 끄지 않는다.
- 새 마이그레이션 `202610270002_notification_reliability.sql`: `replace_reminder_schedule` RPC가 목록을 한 트랜잭션에서 교체한다. 입력 오류 시 기존 예약을 보존한다. 시간대를 저장하고, 서비스 역할만 호출하는 `claim_due_reminders`로 같은 분의 중복 실행을 방지한다. 기존 행은 Asia/Seoul로 보존된다.
- `send-reminders`는 선점 RPC를 사용하고 Push TTL을 60초로 제한한다. 예약 시간대는 계정에서 마지막으로 동기화한 브라우저 기준이다. 여러 시간대의 기기에서 동시에 사용하는 경우는 실제 환경 검증에 포함한다.
- 저녁 안내는 모든 경로에서 “오늘의 루틴을 돌아볼 시간”으로 통일했다. 오래된 완료 기록으로 남은 개수를 단정하던 문구를 제거했다. 완료 여부에 따른 동적 발송 생략은 이번에 보장하지 않는다.

### 미리보기와 남은 출시 조건

예시 데이터 미리보기: `http://127.0.0.1:5191/`. 제품 화면과 스토어를 사용하고 Supabase 요청만 로컬 모형으로 대체한다. 실제 메일·Push·AI·운영 DB를 호출하지 않는다. 테스트로 바꾼 습관 이름과 일기 내용은 원래 예시 값으로 되돌렸다.

4. AI 개발·유료 테스트·운영 배포·스토어 제출은 사용자가 다시 지시하기 전까지 계속 보류한다.

- **비교와 선택:** 서버/기기의 이름·분류·기간·색상·설명·실천 계획을 비교한 뒤 ‘서버 내용 사용’ 또는 ‘내 입력으로 다시 저장’을 선택한다. 기기 입력을 버리는 선택은 별도 확인을 거친다. 재저장도 확인한 서버 버전으로 다시 비교하므로 그사이 바뀌면 재충돌한다. 분류·기간 재적용 전에는 기존 영향 안내를 제공하고, 확인 중 기록·입력·서버 조회 내용이 바뀌면 다시 확인하게 한다. 자동 필드 병합이나 강제 덮어쓰기는 하지 않는다.
- **삭제된 목표:** 남은 입력은 새 ID의 목표로 복사할 수 있다. 진행 중 목표 슬롯을 확인하며 기존 습관·루틴·과거 기록을 새 목표에 자동 연결하지 않는다. 서버에서 삭제된 목표를 편집하던 초안도 원래 주소에서 복원하고 서버 상태 확인 요청을 보낼 수 있다.
- **기기 보관 실패:** 새 목표 저장/삭제 요청은 영속 보관을 성공한 뒤 화면 상태를 바꾼다. 복구 요청을 먼저 보관한 다음 비교했던 이전 요청만 정리한다. 정리 실패·재시작·재충돌에서도 이전 요청이 자동으로 다시 전송되지 않으며 다른 탭의 후속 입력은 임의로 정리하지 않는다. 보관 실패 시 작성 초안·목표·연결을 유지한다.
- **서버 우회 차단:** 새 011 SQL은 `monthly_goals.revision`, 관리자 수정 시 버전 갱신 트리거, `goal_save_receipts`, RPC를 추가하고 인증 사용자의 직접 INSERT/UPDATE 권한을 회수한다. 서버 영수증은 직접 조회/쓰기를 허용하지 않으며 탈퇴 시 계정과 함께 정리된다. 기존 목표 삭제 RPC와 기록 보존 트리거는 유지한다.
