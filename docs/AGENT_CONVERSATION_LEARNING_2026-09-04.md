# 온주 대화 설계 학습 메모 — 2026-09-04

## 범위와 출처

- 사용자가 제공한 `데일리시스템_대화기록_설계자료.md` 전체를 검토했다.
- 이 파일은 원문 대화가 아니라 규칙·샘플·실패 사례 중심 재구성 자료다.
- Claude 공유 링크는 본문 접근에 실패했다. 공유 원문을 검토했다고 주장하지 않는다.
- 본 문서는 설계 분석이다. 모델 가중치 학습, 운영 프롬프트 변경, 배포는 수행하지 않았다.
- 개인의 실제 일정·종교·건강 기록을 모든 사용자의 기본값으로 복제하지 않는다.

## 제품의 중심

온주는 입력칸을 대화로 채우는 설문이 아니라, 합의한 목표와 실제 기록을 비교하며 사용자가 다음 판단을 쉽게 하도록 돕는 비서여야 한다.

사용자가 목적과 속도를 결정하고, 에이전트는 정리·계산·선택지 제안을 주도한다. 능동적 지원과 사용자 주도권은 양립한다.

## 재사용할 행동 규칙

1. 현재 답변이 해결한 내용을 먼저 인정하고, 이미 알려진 내용은 다시 묻지 않는다.
2. 질문 한 개는 물음표 개수가 아니라 사용자가 내려야 할 결정 한 개를 뜻한다.
3. 확정 사실, 합의한 계획, 실제 실행, 추정, 미확인을 구분한다.
4. 예정 시간과 현재 시간을 비교해도 실제 위치·실행 여부를 단정하지 않는다.
5. 목표 구체화는 끝점 → 판정 수치 → 측정 시점·횟수 → 통제 가능성 → 주간 행동으로 진행한다.
6. 기준선이 없으면 미정 상태와 측정 계획을 보존한다. 임의 수치로 필수 칸을 채우지 않는다.
7. 외부 의존성이 있는 목표에는 사용자가 통제할 중간 마감과 여유를 제안한다. 예시 문서의 외부 서비스 규정을 현재 사실로 재사용하지 않는다.
8. 미실행, 시간 변경, 측정 중단, 선택 항목 생략, 미기록은 서로 다른 상태다.
9. 점검은 합의한 기본 계획에서 달라진 부분을 우선 묻는다. 매번 전체 일정을 다시 설계하지 않는다.
10. 한 번의 실패로 구조를 바꾸지 않는다. 반복 관찰은 사실로 설명하되 인과관계를 확정하지 않는다.
11. 구조 변경은 제안과 사용자 승인 뒤에 적용하고 규칙 이력을 남긴다.
12. 사용자의 요청이 있더라도 위협·수치심·종교적 처벌을 동기부여 수단으로 쓰지 않는다.
13. 외부 기록은 확인한 출처·시간 범위·본문 조회 여부를 구분한다. 검색 실패를 활동 부재로 단정하지 않는다.
14. 저장 성공이 확인된 뒤에만 '기록했습니다'라고 말한다.

## 자료 내부에서 조정해야 할 부분

- '수주간 기다린다'와 '사흘이면 구조 제안'이 공존한다. 3일을 모든 항목의 보편 임계값으로 쓰지 않는다. 짧은 반복은 관찰 신호이며, 개편 조건은 사용자와 합의한 항목별 정책으로 둔다.
- 사용자 주도 대화는 비서가 수동적으로 설문만 하라는 뜻이 아니다. 계산과 초안은 비서가, 승인과 우선순위는 사용자가 담당한다.
- 선택/일반/중요 항목 구분은 사용자가 설정한다. 특정 신앙 항목을 모든 고객에게 강제하지 않는다.
- 4일짜리 한 사용자 사례로 일반 고객의 성취율이나 최적 기간을 입증할 수 없다.

## 현재 코드에서 확인한 간극

`supabase/functions/onju-agent-v2/index.ts` 및 `web-mvp/scripts/run-agent-evals.mjs` 검토 기준.

- 도구 실행 후 다음 Responses 요청에 `instructions`를 다시 전달하지 않는다. 최종 답변에도 행동 지침과 최신 사실을 일관되게 전달하는 경로를 먼저 점검해야 한다.
- 저장된 메시지를 읽지만 응답 연결 복구 시 명시적으로 재구성해 보내지 않는다. 응답 ID 실패를 단순 재시도로 처리하는 대신 최근 대화·확정 사실·미해결 질문을 복원해야 한다.
- '없어' 같은 단어가 포함되면 단계가 끝날 수 있다. '월요일은 없지만 화요일에는 있어' 같은 발언은 단계 완료가 아니다.
- 데이터 모델은 일정과 단일 목표 카드 중심이며, 사용자별 행동 규칙·실행 기록·미확정 정보·측정 목적·규칙 변경 이력은 별도 모델링이 필요하다.
- 현재 평가는 단계, 블록 수, 키워드 등 최종 결과 중심이다. 질문 적절성, 근거 없는 단정, 중간 턴 오류, 수정 이후 기억 유지, 장기 점검 품질을 충분히 검증하지 않는다.
- 따라서 기존 테스트 통과는 대화 비서 품질 전체가 검증됐다는 뜻이 아니다.

| 상황 | 기대 행동 | 실패 조건 |
| --- | --- | --- |
| 운영을 안정화하고 싶다 | 완료 상태를 하나의 질문으로 구체화 | 기간부터 강제로 입력 요구 |
| 회의 안건 1건 이하 | 언제, 한 번인지 지속인지 차례로 확인 | 임의 측정 기간을 확정 |
| 기준선은 다음 측정 후 정한다 | 미정과 측정 계획 유지 | 수치를 만들어 저장하거나 진행 차단 |
| 출발 예정 이후에 아침 점검 | 이동 중일 가능성을 고려해 짧게 질문 | 현재 위치를 단정 |
| 아침 루틴 시간이 어긋났다 | 미실행인지 시간 변경인지 확인 | 곧바로 실패 판정 |

| 측정 도중 중단했다 | 사전 측정 목적에 비추어 해석 | 무조건 실패 또는 성공으로 포장 |
| 점심 점검 | 짧게 기록하고 마무리 | 장문의 코칭과 구조 변경 |
| 한 소스에서 기록을 못 찾았다 | 조회 범위와 한계 명시 | 하루 전체 활동이 없다고 단정 |
| 일정 일부가 없다고 말했다 | 나머지 일정 계속 수집 | 전체 단계 자동 종료 |
| 사용자 규칙을 수정했다 | 새 규칙과 적용 범위 보존 | 과거 규칙으로 되돌아감 |

## 적용 순서

1. 현재 동작을 위 시나리오로 기준 측정한다. 예시 문장 그대로의 테스트와 새로운 표현의 검증 세트를 분리한다.
2. 모든 모델 호출의 지침·문맥 전달과 실패 복구를 바로잡는다.
3. 목표 협의 및 실제 점검용 행동 지침과 짧은 대화 예시를 분리한다.
4. 실행·미확정·규칙·측정 목적을 사용자별 기억으로 저장한다.
5. 다중 턴 수정·예외·며칠 뒤 재개까지 검증한 뒤 배포한다.
