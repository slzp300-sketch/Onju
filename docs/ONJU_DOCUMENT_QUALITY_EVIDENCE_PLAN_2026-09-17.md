# 온주 문서급 품질 — 합격 기준과 근거 수집 절차

작성: 2026-09-17. 승인된 작업: 무료 기준 정리·실패 경로 보완·검사 준비. 이번 작업은 유료 호출, 공개 배포, 모델 교체를 포함하지 않는다.

## 1. 완료의 의미

사용자 목표는 원문의 문장을 복제하는 것이 아니라 **사용자 이해 → 필요한 정보 확인 → 이유와 실행 방법이 분명한 계획 → 수정과 관리**가 자연스럽게 이어지는 경험이다.

합격 기준의 단일 원본은 [기준 파일](agent/coaching-document-quality.json)이다. 기존 코드 테스트 통과나 답변 길이, 작성한 예시 답변의 점수로 실제 품질을 대신하지 않는다. 기존 상세 검토는 [유료 품질 검토](agent/coaching-paid-review.json)에 보존한다.

| 항목 | 2점(충족) 근거 | 대표 실패 |
| --- | --- | --- |
| 사용자 이해·사실 근거 | 현재 수준·선호·제약 때문에 제안이 어떻게 달라지는지 실제 답변에서 확인 | 사용자 정보를 다시 말하기만 함, 장비·기간 임의 가정 |
| 필요한 정보 요청 | 이미 받은 것은 생략하고 계획을 바꾸는 미확인 정보만 함께 요청 | 반복 질문, 미확인 상태에서 숫자 실행안 생성 |
| 설명의 깊이 | 필요한 시점에 방법·이유·기간별 진행·기록 예시·조정·복귀를 설명 | 긴 인사·요약만 제공, 기록하면 관리해준다는 약속만 반복 |
| 실행 가능성 | 행동·분량·순서·휴식과 시간 배분이 맞고 바로 따라 할 수 있음 | 어느 세트에 추가할지 불명확, 전체 시간 초과 |
| 수정·관리 | 요청 범위만 바뀌고 기록이 다음 판단에 활용됨; 승인·재접속 보존 | 다른 행동 변경, 기록을 무시하고 설문 재시작 |
| 가독성·전달 | 핵심 행동과 상세 설명이 실제 화면에 보이고 저장 내용과 일치 | 생성 후보만 존재, 오류로 미전달, 표시 중 설명 유실 |

0점=실패, 1점=일부 충족, 2점=근거를 들어 충족, 미검증=null. 적용되는 항목은 모두 2점이어야 하며 중대 실패는 평균점수로 상쇄하지 않는다. 필요한 시점이 아닌 항목은 미리 정한 단계별 적용표에 따라 제외한다. 평가 후 유리하게 적용 항목을 바꾸지 않는다.

**사용자 결정 유지:** 정보가 부족하면 실행 초안을 먼저 만들지 않는다. 필요한 정보를 한 번에 묻되 이미 알고 있거나 거절한 정보는 제외한다. 어떤 도움을 제공할 수 있는지와 좋은 접근 방향은 제안할 수 있다. 실행 방법·이유·관리는 충분히 설명한다. 화면의 메인 목표와 행동은 간단하게 유지한다.

## 2. 무료 준비와 실답변 합격을 분리한다

- `offline_prepared_awaiting_paid_approval`: 알려진 구조 결함과 회귀 검사를 통과하고, 유료 근거 수집을 요청할 준비가 됨.
- 실제 문서급 합격: 최신 버전에서 생성·전달된 실제 답변과 후속 흐름을 사람이 검수하고 사용자가 최종 승인함.
- 첫 상태가 두 번째 상태나 유료 지출 허가를 뜻하지 않는다. 현재 70% 사전 검토 장치는 그대로 유지한다.
- 이번 진행 동의만으로 70% 조건 변경이나 새 예산을 승인받았다고 해석하지 않는다. 다음 실제 근거 수집은 **수정된 진입 조건·회차 한도·범위·중단 조건을 별도로 승인**받는다.

최종 목표는 70점짜리 대화가 아니다. 70%는 기존의 유료 검사 진입 조건이며 최종 품질 점수와 다르다.

## 3. 최소 실제 평가 흐름

1. 원문 사용자 발언 1~3을 그대로 재생한다. 원문 AI 답변은 입력하지 않는다. 온주 질문에 없는 번호를 참조하는 표현은 해석 불가능한 부분으로 표시하고 원문의 뜻을 모델에 몰래 보충하지 않는다.
2. 원문에 없는 기간·시간·장비·제약을 가상 보충 발언으로 명확히 구분한다. 부족한 조건이 더 있으면 미리 준비한 사용자 정보 범위에서만 답한다. 추가 턴·비용을 기록한다.
3. 상세 계획의 실제 전달·저장·모바일 화면 표시를 확인한다. 모델이 후보를 생성했어도 앱에서 거절됐다면 전달 실패다.
4. 생성된 계획에서 식별 가능한 행동 하나를 골라 부분 수정을 요청한다. 예시는 ‘근력 A의 턱걸이만 줄여줘’지만 실제 계획에 없는 제목을 만들어 입력하지 않는다. 요청하지 않은 목표·시간·빈도·다른 행동의 보존을 확인한다.
5. 미승인 상태를 확인한 후 **표시된 초안 ID에 연결된 명시적 승인**을 사용한다. 승인·재접속은 추가 모델 호출 없이 검사한다. 실제 DB/브라우저 확인 전에는 로컬 직렬화 검사만으로 서버 저장 성공을 주장하지 않는다.
6. 실제 수행량과 어려움을 가상 보고하고, 기록 저장과 다음 실행 제안을 확인한다. 보고된 내용만 기록하며 계획 변경은 다시 승인받는다.

기본 구성은 모델을 사용하는 대화 6턴과 승인·재접속 확인 1단계다. 턴과 모델 호출 수는 다르며 1턴에 여러 호출이 생길 수 있다. 한 턴 실패 또는 비용/통신 불확실 시 자동 반복하지 않는다. 불충분한 답변을 통과할 때까지 재생성하지 않고 실패 자료를 보존한다.

## 4. 기록할 증거

- 코드·화면·검수 도구 버전과 SHA-256. 표시 코드 변경도 기존 검토를 무효화한다.
- 실제 사용자 입력과 출처 구분: 원문 / 가상 보충 / 가상 수정 / 가상 실행 보고.
- 수정하지 않은 제공자 응답, 호출 ID, 모델, 사용량, 시간 초과와 재작성 횟수.
- 실제 화면 답변, 저장된 상태, 승인 전후 변경점, 재접속 후 상태, 모바일 화면 검사.
- 각 합격 항목의 답변 근거 구절과 검수 이유. 빈 검수표는 항상 ‘미검증’이다.
- 관측 사용량 기반 추정 비용, 미확인 예약액, 잔여 한도. 미확인 예약액을 실제 청구액이나 0원으로 표시하지 않는다.

개인 대화와 세션 접속 자료는 비공개 로컬 검사 자료로만 다룬다. 작업로그/공통 프롬프트/공개 번들에는 원문 대화나 비밀키를 넣지 않는다.

## 5. 실패별 다음 작업

| 실제 실패 | 먼저 살펴볼 곳 | 무료 확인 | 새 생성이 필요한 근거 |
| --- | --- | --- | --- |
| 사용자의 뜻·정정 오해 | 입력 맥락·도구 선택·기억 | 알려진 경로 재현, 원문 근거 검사 | 실제 의미 해석의 개선 |
| 설명이 얕거나 모호 | 요청 깊이·예시·출력 여유·상충 지침 | 설명 유실과 계산 오류, 지침 충돌 | 방법·이유·관리 설명의 질 |
| 좋은 후보가 미전달 | 검증·시간 제한·저장·렌더러 | 정상 후보 수용/잘못된 후보 차단 | 최신 규약을 실제 모델이 준수하고 끝까지 전달 |
| 후속 수정·관리 실패 | 승인 상태·부분 수정·기록 도구 노출 | 작성한 도구 응답으로 보존·저장 경로 검사 | 실제 모델의 대상 선택·기록 해석·다음 조정 |

원인 하나를 수정하고 해당 실패를 재검사한다. 모델 교체·파인튜닝·다중 에이전트는 근거 없이 추가하지 않는다. 새 답변 생성이 필요한 구간만 별도 예산 내에서 확인한다.

## 6. 반복·다른 사례·최종 검수

핵심 흐름 통과 후 별도 예산으로 같은 사례 반복과 개발에 사용하지 않은 조건/표현 사례를 검사한다. 새 회차에서는 성공만 고르지 않고 모든 시도를 남긴다. 원문/온주 비교는 문장 유사도보다 위 기준과 실제 실행 가능성을 기준으로 판정한다. 다른 분야까지 검사하지 않았다면 운동 사례의 결과를 온주 전체 품질로 일반화하지 않는다.

재현님의 최종 확인과 검사 범위 명시가 있어야 해당 범위의 완료로 기록한다. 모든 미래 답변의 완벽함이나 의료·운동 전문성 인증을 뜻하지 않는다.

## 7. 실행 도구와 최신 결과

- 무료 전체 검사: `node web-mvp/scripts/verify-offline.mjs`
- 저장 응답 재검사: `node logs/reference-replay/audit-saved-depth-offline.mjs`
- 준비 보고서: `node web-mvp/scripts/prepare-coaching-evidence.mjs --offline-summary <검사 summary.json> --saved-summary <재생 summary.json>`
- 마지막 명령은 외부 통신을 차단하고, 현재 버전과 두 검사 결과를 비교해 준비 상태·비용 참고치·빈 검수표만 생성한다. 유료 호출을 허가하거나 실답변에 점수를 주지 않는다.

검사 결과와 비용은 [이번 작업로그](WEB_MVP_WORKLOG_2026-09-17_DOCUMENT_EVIDENCE_READINESS.md)에 기록한다.

평가 설계 참고: [OpenAI 평가 지침](https://developers.openai.com/api/docs/guides/evaluation-best-practices)의 작업별 기준, 실제 결과 기록, 인간 검수 결합 원칙을 사용했다. 새 유료 평가 플랫폼은 도입하지 않는다.
