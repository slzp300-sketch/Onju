# 온주 — 11차 진단 1~6번 수정 및 제약 구조 보완

작성: 2026-09-16 · 요청: “1-6번 우선 해결 진행하고 구조적으로 이런 문제가 있다면 개선하자”

## 작업 범위

대상은 `logs/sites/onju-web-mvp/supabase/functions/onju-agent-v2/`의 Site 제품이다. 루트 앱·루트 Edge Function의 기존 미커밋 변경은 건드리지 않았다. 배포, 운영 DB 변경, 공급자 API 호출, 커밋·푸시, 노션 등록은 하지 않았다.

이번 문제에는 공통 구조가 있다. **같은 숫자를 찾아내는 것**과 **그 숫자가 완료량인지, 누구의 시간인지, 어느 목표에 적용되는 제한인지 판단하는 것**이 충분히 분리되지 않았다. 요약에 남은 주간 합계만으로 원래 일별 제한을 대체하거나, 반대로 관계없는 설명까지 제한으로 묶는 경우도 있었다.

기존 모델·프롬프트에 고정 답변을 추가하지 않았다. 모델의 후보를 받는 저장 경계와 초안·수정·승인의 공통 계산 경계에 의미 역할과 독립 제한을 적용했다. 모든 자연어를 이해하는 새 모델을 개발하거나 재학습한 작업은 아니다.

## 1~6번 처리

| 번호 | 진단 문제 | 수정 방식 |
|---|---|---|
| 1 | `월·수·금`, `Mon, Wed, Fri`의 반복 요일 손실 | 공통 요일 정규화 사본을 수량 환산과 일별 제약에 함께 사용. 저장 원문은 유지하고 불완전 목록은 미해석 처리 |
| 2 | 남은 5개를 완료한 5개로 저장 | `remaining` 역할 추가. 완료·진행 중·남음·목표량 구분. 명시된 남은 상태는 보존하되 완료량처럼 차감하지 않음 |
| 3 | 디자인만의 80분을 전체 목표 시간으로 저장 | 시간 소유자와 목표 적용 범위를 별도 분류. 여러 목표 중 일부의 예산을 공통 시간에 저장하는 후보 거절 |
| 4 | 주간 총량과 하루 상한을 동시에 적용하지 못함 | 주간·일별·회당 제한의 논리적 결합. 각 한도를 따로 유지하고 모든 한도를 만족하는 실행안만 허용 |
| 5 | 설명용 `시간/time`을 미해석 수량으로 판단 | 가용·사용할 시간 등 문맥상 명사를 별도 처리. 지원하지 않는 나머지 수량 단위는 계속 차단 |
| 6 | 두 목표의 합산을 두 사람의 합산으로 판단 | `combined` 단어 자체가 아니라 사람의 공동 시간인지 목표의 합계인지 구분 |

### A. 역할·소유자·적용 범위

- `goalFactBinding.ts`: 수량별 역할에 `remaining` 추가. `8개 중 3개 완료, 5개 남음`의 5개를 평범한 완료량 후보로 저장할 수 없다.
- 명시적으로 ‘5개 남음’을 현재 상태로 저장하는 것은 가능하다. 단, 현재 완료량이 확인되지 않은 상태에서 `목표 8 - 완료 5` 같은 계산을 하지 않는다.
- 예전 데이터에 잘못된 숫자 요약과 원문이 함께 남아 있으면, 원문의 남은/미완료 역할을 근거로 잘못된 차감을 막는다. 이미 사라진 원문을 복원하지는 않는다.
- 새로운 `goalBudgetScope.ts`: 개인/공동 소유와 전체/특정 목표 적용을 분리한다. 근처 다른 목표의 완료 실적 문장은 가용 시간의 소유자로 연결하지 않는다.
- 기존 단일 목표가 다중 목표로 바뀐 뒤 불러올 때도 범위를 다시 검증한다. 저장된 `binding` 속성을 임의로 바꿔도 근거에서 다시 만든다.
- 여러 목표의 개별 예산을 저장·배분하는 완전한 UI/스키마는 이번 범위가 아니다. **개별 예산을 잘못된 전체 예산으로 승격하지 않는 보호**를 구현했다. 전체 예산인지 개별 배분인지 대화로 명확히 할 필요가 남을 수 있다.

### B. 표시 요약과 독립 한도

- 새로운 `goalCapacityConstraints.ts`: 언어별 문구가 아니라 정규화된 주간·일별·회당 제한을 결합한다.
- 예: 주 60분 + 하루 20분이면 20분씩 3일은 허용하고, 하루 30분 또는 20분씩 4일은 차단한다.
- 예: 주 90분 + 주 2회 + 회당 20분이면 표시된 주간 90분을 임의로 40분으로 고치지 않는다. 세 제한을 함께 보존하고 실행은 회당·횟수 제한도 만족해야 한다.
- 횟수만 알 때 분 단위 시간을 만들어내지 않는다. 수요일 0분 같은 예외를 적용해도 원래 주간 한도가 늘어나지 않는다.
- 같은 범위의 중복·정정 가능성이 있는 예산이나 `or/if/또는` 조건을 단순히 더하거나 한쪽만 선택하지 않는다.

### C. 짧은 인용과 재로딩

- `goalCapacityContract.ts`: 모델이 주간 총량만 짧게 인용해도 연결된 하루·회당 제한을 포함한다. 원문에서 한도를 다시 계산하여 캐시된 수치가 권한이 되지 않게 한다.
- 다른 사람의 예시나 부부 합산 예산을, 명시적으로 밝힌 개인 몫에 다시 합치지 않는다.
- 주체 전환을 다루는 `goalEvidenceScope.ts`는 수량 설명 뒤의 `, I ...`를 분리하되 `coding, I completed ...` 같은 목표 소개나 `between us, we ...` 같은 소유자 소개, 조건문은 잘라내지 않는다.
- 잘못된 형식의 저장된 원문은 예외로 서비스가 종료되는 대신 미해석으로 처리한다.
- 같은 제약을 `goalBriefDecisionView`, 타당성 계산, 기존 초안·수정·승인의 공통 검사에서 사용한다. DB 마이그레이션은 없다.

## 비용·운영·한계

공급자 API 호출 0회, 추가 모델 API 비용 $0. 외부 네트워크 차단과 작성된 모의 공급자 응답을 사용했다. Codex 자체 사용량이나 과거 청구 총액이 0이라는 뜻은 아니다.

가상 설정 205명은 실제 참여자 205명이 아니다. 실제 모델이 자발적으로 문맥을 추출하고 자연스럽게 답하는지, 실사용자가 편해졌는지는 이번 검사만으로 입증할 수 없다. 모델 품질·속도·실사용 만족도 검증은 별도다.

불확실하거나 아직 지원하지 않는 표현은 멋대로 한도를 완화하지 않는다. 모든 자연어 표현과 모든 예외를 지원한다는 완료 선언이 아니라, **보고된 6유형과 이번에 정의한 구조 불변성의 검증**이다. 운영 사이트는 아직 바꾸지 않았다.
