## 검사 방법과 증거 수준

1. **일반 여정**: 사람이 말할 법한 문장과 그 문장에서 추출돼야 할 구조화 인자를 사람이 작성했다. 실제 Site의 `updateGoalBrief` → JSON 왕복 → `loadGoalBrief`와 현실성 계산 함수를 실행했다. 원문 보존·수정·누락 상태 등을 확인했다.
2. **잘못된 모델 후보 방어**: 모델이 잘못 추출했다고 가정한 인자를 의도적으로 넣었다. 이 검사의 실패는 ‘실제 모델이 오해했다’가 아니라 ‘그런 오해를 서버가 막지 못한다’는 뜻이다.
3. **기능 공백**: 목표 하나 제외는 현재 기록 도구가 그 의도를 표현할 수 있는지를 검사했다. 일부 필드를 남겨 보내는 것을 삭제 명령으로 보장한 API가 아니므로 일반 정상 입력 거절과 분리했다.
4. **실제 에이전트 경로**: `runAgentTurn`을 실행하되 모델 요청 함수만 작성된 도구 호출로 대체했다. 앞단 필터·도구 활성화·저장·최종 표현의 연결을 검사했다. 실제 모델 응답은 `null`이고 만들어 둔 문구가 포함된 결과는 `renderedReplyFromFixture`로 별도 표기했다.
5. 네트워크 차단기를 항상 불러왔다. 외부 DB·배포·사용자 자료를 읽거나 수정하지 않았다. 모든 검사 전후의 코드·입력 지문을 비교했다.

## 발견 사항 — 우선순위별 6개 유형

### 1. 명시적으로 바꾼 영어 기간을 에이전트가 무시함 — P1

- 사례: US-04. 기존 기간 `3 months`(13주), 새 요청 `Change the timeframe to 8 weeks.`.
- 하위 목표 정보 함수에서는 8주로 수정된다. 그러나 실제 `runAgentTurn`에 같은 올바른 후보를 넣으면 **13주·3 months가 유지**된다.
- 작성된 응답 문구를 처리한 최종 결과의 서버 추가 기간 표시도 `Timeframe: 3 months`였다. 이 문구는 실제 모델의 답변을 관측한 것이 아니다.
- 원인: [agent.ts:737](../logs/sites/onju-web-mvp/supabase/functions/onju-agent-v2/agent.ts#L737)에서 이미 기간이 있으면 새 기간 후보를 무조건 `null`로 바꾼다. 한국어의 별도 자동 기간 감지와 영어 처리 차이까지 겹친다.
- 개선: 사실 추가와 명시적 정정을 분리하고, 기간 변경 근거가 있을 때 기존 값 보호를 해제해야 한다. 변경하지 않은 목표·기준은 그대로 보존해야 한다.
- 완료 기준: 한국어/영어의 동일한 기간 변경이 실제 에이전트·저장/복원·표시에서 모두 일치하고, 단순 후보 질문으로는 변경되지 않는다.

### 2. 이미 아는 상태를 ‘미측정’으로 바꾸는 보호 허점 — P1

- 사례: KR-05의 `측정한 점수는 65점`, US-05의 `I am not a complete beginner.`.
- 의도적으로 잘못된 `unmeasured` 후보를 주었을 때 서버가 이를 받아들여 기존 점수/독서 기록을 ‘첫 주 측정 필요’로 바꾼다. 두 경우 모두 하위 함수와 실제 에이전트 경로에서 재현했다.
- 원인: [goalIntakeEvidence.ts:12](../logs/sites/onju-web-mvp/supabase/functions/onju-agent-v2/goalIntakeEvidence.ts#L12)의 한국어 조건은 ‘측정’만 있어도 참이 될 수 있다. 영어의 `complete beginner` 판정도 앞의 `not a` 부정을 구분하지 않는다.
- 개선: 측정/미측정의 긍정·부정, 어떤 사실에 대한 진술인지, 기존 값의 정정 근거를 구분해야 한다. 단어 포함 여부만으로 알려진 수치를 버리지 않는다.
- 완료 기준: 알려진 수치를 유지하고, ‘이전 점수가 잘못됐다/측정한 적이 없다’처럼 명확히 정정한 경우는 허용한다. 잘못 추출한 후보 때문에 사용자에게 같은 정보를 재질문하지 않는다.

### 3. 현재 수준을 모른다는 말을 가용 시간도 모른다는 뜻으로 저장 — P1

- 사례: KR-09. 실행 시간을 물어볼 차례에 사용자가 `현재 기록 수준은 잘 모르겠어.`라고 말한 상황.
- 잘못된 모델이 이를 `capacity`로 보내면 하위 함수는 가용 시간으로 받아들이고, 미입력 여건이 채워진 것처럼 `missing=null`을 반환한다.
- 원인: [goalBrief.ts:235](../logs/sites/onju-web-mvp/supabase/functions/onju-agent-v2/goalBrief.ts#L235)와 [agent.ts:718](../logs/sites/onju-web-mvp/supabase/functions/onju-agent-v2/agent.ts#L718)는 ‘현재 여건 질문을 기다린다’는 상태만으로 다른 표현을 허용한다.
- 개선: 기다리는 질문보다 실제 발언의 대상이 우선해야 한다. 현재 수준과 가용 시간의 근거를 혼용하지 않는다.
- 완료 기준: 이 발언은 현재 수준 정정으로만 처리하고, 아직 말하지 않은 실행 시간은 비워 둔다. ‘시간도 모르겠다’라고 명시한 경우와 구분한다.
- 제한: 이 사례의 실패는 하위 함수에서 실행했다. 실제 에이전트의 동일 조건은 코드로 대조했지만, 이 사례를 별도 전체 경로로 실행한 결과라고 집계하지 않았다.

### 4. 자연스러운 영어 가용 시간 표현이 누락됨 — P1

- 사례: US-03. `Some weeks I only get two 15-minute windows.`.
- 현재 수준보다 먼저 시간을 말하면 하위 함수는 `capacity_requires_grounded_user_evidence`로 거절한다. 실제 에이전트 경로에서는 여건 후보를 제거하고 시간 없이 다음 질문을 보낸다.
- 더 정형적인 `My available time is about 30 minutes per week.`는 받아들인다. 같은 의미라도 특정 표현/입력 순서에 의존한다.
- 원인: [goalIntakeEvidence.ts:5](../logs/sites/onju-web-mvp/supabase/functions/onju-agent-v2/goalIntakeEvidence.ts#L5)의 용어 목록과 슬롯 순서 예외가 충분하지 않다.
- 개선: 영문 표현을 하나씩 추가하는 데 그치지 않고 시간량·빈도·유동성·원문 근거를 구분한 구조화 후보와 일관된 검증으로 처리한다.
- 완료 기준: 두 문장을 모두 추정 가능한 여건으로 저장하되, ‘매주 고정 30분’이나 특정 요일/시각으로 단정하지 않는다.

### 5. 영어 수량·속도 비교가 빠져 무리한 목표를 ‘준비됨’으로 분류 — P1

- 사례: US-06. 현재 `1 article per week`, 목표 `publish 12 articles`, 기간 4주, 여건 주 1시간.
- 내부 계산은 주당 3편이 필요하다는 충돌을 만들지 않고 `ready`를 반환한다. 같은 계산 구조의 한국어 KR-08은 `strained`와 조정 필요 상태를 반환한다.
- 원인: [goalFeasibility.ts:30](../logs/sites/onju-web-mvp/supabase/functions/onju-agent-v2/goalFeasibility.ts#L30)의 수량 단위와 주간 속도 해석이 한국어 중심이다. 파싱 실패로 비교를 건너뛴 뒤 준비 상태로 내려간다.
- 개선: 원문과 별개로 값·단위·누적/속도·기준 기간을 정규화한다. 비교 불가능한 상태를 ‘검토 완료’로 간주하지 않는다.
- 완료 기준: 같은 수치의 한영 표현이 같은 판단을 내리고, 계산할 수 없으면 추가 측정/확인이 필요하다고 표시한다. 이 테스트는 실제로 사용자가 주 3편을 쓸 수 없다는 증거가 아니라 **검토할 충돌을 놓치는 문제**다.

### 6. 여러 목표 중 하나만 제외하는 동작이 명확하지 않음 — P2, 기능 공백

- 사례: KR-07. `독서 목표는 빼고 포트폴리오만 남겨줘.`.
- `record_goal_brief`가 표현할 수 있는 남길 분야만 보내도 `areas`, `objectives`, `baselines`에 독서가 남는다.
- 원인: [goalBrief.ts:207](../logs/sites/onju-web-mvp/supabase/functions/onju-agent-v2/goalBrief.ts#L207)의 분야 처리는 추가 중심이다. 목표 정보 도구에는 특정 분야 삭제/보류라는 명시적 동작이 없다.
- 개선: 추가·수정·제외·보류·재개를 구분한 동작과, 연결된 현재 수준·결과·우선순위 정리 규칙이 필요하다. 삭제와 잠시 미루기를 임의로 동일시하면 안 된다.
- 완료 기준: 제외 요청의 대상만 변경하고 나머지 목표와 원문 기록을 보존한다. 관계없는 일정·다른 목표가 함께 지워지지 않는다.
- 제한: ‘목표 한 개만 남긴 배열을 보내면 반드시 교체돼야 한다’는 기존 계약을 주장하는 것이 아니다. **요구를 명확히 표현할 도구가 부족한 것**으로 분류했다. 실제 모델의 선택·최종 대화는 평가하지 않았다.

## 이번에 확인된 강점과 미측정 부분

확인된 범위에서는 취업 준비 목표 6개→3개 수정, 한국어 미확정 기간 거절, 양육으로 인한 시간 유동성 보존, 한국어 홍보 글의 과도한 속도 감지와 목표 하향이 처리됐다. 모든 예외 표현·사용자의 만족도까지 검증한 것은 아니다.

재접속은 JSON 저장·복원 경계 검사이며 실제 브라우저/DB 재접속이 아니다. 육아·돌봄·직무 상황에 적절한 공감, 화면 가독성, 계획 실행 여부, 장기간 재방문은 미측정이다. 가계부 사례는 기록 목표 처리 검사이며 재무 조언이나 개인정보 보호 전반의 검증이 아니다.

## 왜 기존 검사 통과 후에도 문제가 발견됐나

이전 5명은 영어 기간의 **최초 저장과 복원**을 검사했지만, 새 사례는 이미 정한 기간을 **나중에 변경하는 실제 에이전트 경로**를 검사했다. ‘모르겠다’를 인식하는지와 ‘알고 있는데 잘못 추출한 모름 후보를 막는지’도 다르다. 현재 수준을 묻던 단계와 시간 여건을 묻던 단계에서 같은 문장을 보내는 경우 역시 다르다.

따라서 앞선 결함 수정이 사라진 것이 아니라, 테스트 범위 밖에 있던 조건이 추가된 것이다. 다만 반복되는 문제의 방향은 분명하다. **문자열 패턴·질문 순서에 과도하게 의존하는 검증과, 명시적 변경/제외 동작의 부족**을 함께 개선해야 한다. 모델만 바꾸거나 예시 문장만 계속 늘리는 것으로 해결됐다고 판단하면 안 된다.

## 권장 보완 순서 — 아직 구현하지 않음

1. 원문에서 어떤 사실을 추가/정정/철회한 것인지 구분하고, 이미 알려진 값을 보호하면서 명시적 정정은 허용한다. 기간 변경과 긍정/부정 처리부터 보완한다.
2. 현재 수준·시간 여건의 근거를 분리하고, 한영 수량·빈도·단위를 공통 구조로 검증한다. 해석하지 못한 값은 ‘검증 완료’가 아닌 확인 필요로 남긴다.
3. 여러 목표의 제외/보류/재개와 연관 정보 정리 규칙을 명시한다.
4. 이번 10명과 기존 5명의 같은 입력을 회귀 검사로 유지한다. 하위 함수와 실제 에이전트 경로를 함께 검사한다.
5. 이 보완 후에 운영 준비 점검과 별도 비용 상한을 승인받은 실제 모델 품질 평가로 돌아간다.

현재는 진단 요청이므로 제품 코드를 수정하거나 위 계획을 자동 실행하지 않았다.
